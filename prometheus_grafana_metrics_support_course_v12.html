1. Наблюдаемость и роль прикладной поддержки

Метрики, логи, трейсы — чем отличаются

СигналЧто показываетПример вопросаКогда нужен поддержке
МетрикиЧисловые значения во времени.Сколько ошибок 5xx за 5 минут?Для алертов, трендов, SLA/SLO, сравнения до/после релиза.
ЛогиСобытия и текстовые сообщения приложения.Какая конкретная ошибка была в stack trace?Для детализации причины после обнаружения симптома по метрикам.
ТрейсыПуть запроса между сервисами.На каком сервисе выросла latency?Для распределённых систем, где один запрос проходит несколько компонентов.

Как думать при инциденте

  1. Есть ли симптом? Ошибки, latency, падение throughput, рост очередей.
  2. Где масштаб? Один pod, один namespace, один endpoint, весь кластер.
  3. Когда началось? Сравнить с релизом, изменением конфигурации, пиком нагрузки.
  4. Что первично? Например, рост latency мог вызвать рост 5xx, а не наоборот.
  5. Что подтверждает гипотезу? Метрика + лог + событие деплоя лучше одной красивой панели.
Правило: один график редко доказывает причину. Он показывает направление расследования.

2. Устройство Prometheus

Что такое Prometheus

Prometheus — система мониторинга временных рядов. Она периодически опрашивает цели, сохраняет значения метрик с timestamp и labels, позволяет писать запросы PromQL и формировать алерты.

Приложение / Exporter ↑ endpoint /metrics, /prometheus или /actuator/prometheus | Prometheus scrape loop | +-- Service Discovery +-- Relabeling +-- TSDB blocks / WAL +-- PromQL API +-- Alerting rules | Grafana / Alertmanager / API clients

Ключевые компоненты

КомпонентЗадачаАналогияЧто важно поддержке
Scrape loopРегулярно забирает метрики с targets.Обходчик, который снимает показания счётчиков.Проверять up, scrape_duration_seconds, scrape_samples_scraped.
Service DiscoveryНаходит targets в Kubernetes, файлах, Consul и других источниках.Адресная книга.Если target пропал — проверить discovery и labels.
TSDBХранит временные ряды локально блоками.Архив показаний.Следить за местом на диске, cardinality, retention.
PromQL engineВыполняет запросы по метрикам.Аналитик, который считает скорость, процентили и агрегации.Уметь читать запросы в панелях и алертах.
RulesRecording rules и alerting rules.Регламент расчётов и тревог.Понимать, почему алерт сработал и какие series участвовали.
AlertmanagerГруппирует, подавляет и маршрутизирует алерты.Диспетчер уведомлений.Проверять route, silence, inhibition, receivers.

Особенность Prometheus

Prometheus в классическом сценарии сам забирает метрики по pull-модели. Это удобно: мониторинг контролирует частоту опроса, видит, какие targets живы, и может обнаружить недоступность через метрику up.

Для поддержки: если приложение не отдаёт endpoint с метриками, Prometheus не сможет «угадать» значения. Проверяйте не только /metrics, но и /prometheus или /actuator/prometheus — фактический путь зависит от фреймворка и настройки scrape.
Ограничение: Prometheus локально хранит time series. Для долгого хранения, глобальных запросов и высокой доступности часто добавляют Thanos, Mimir, Cortex или VictoriaMetrics.

2.1 Scrape, targets, exporters

Как Prometheus получает метрики

1. Найти target
Prometheus получает список целей через service discovery или статическую конфигурацию.
scrape_configs:
- job_name: payment-api
  static_configs:
  - targets: ['payment-api:8080']
2. Опросить endpoint метрик
По расписанию scrape_interval Prometheus делает HTTP-запрос к endpoint. Частые варианты: /metrics, /prometheus, /actuator/prometheus.
curl http://payment-api:8080/metrics
curl http://payment-api:8080/prometheus
curl http://payment-api:8080/actuator/prometheus
3. Разобрать samples
Каждая строка становится sample: имя метрики, labels, значение, timestamp.
http_requests_total{method="GET",code="200"} 15342
4. Сохранить time series
Уникальная комбинация metric name + labels создаёт отдельный временной ряд.

/actuator/prometheus в Spring Boot

/actuator/prometheus — частый endpoint для приложений на Spring Boot с Actuator и Micrometer. Он отдаёт метрики приложения в формате Prometheus: HTTP-запросы, JVM, пул потоков, базы данных, бизнес-счётчики и пользовательские метрики.

Для поддержки: если в документации сервиса указан Actuator, то вместо обычного /metrics Prometheus часто опрашивает именно /actuator/prometheus. Также в некоторых сервисах встречается путь /prometheus. Это нужно проверять при пропаже данных на панели.
Что проверитьКоманда / примерЧто означает проблема
Endpoint отвечаетcurl http://payment-api:8080/metrics
curl http://payment-api:8080/prometheus
curl http://payment-api:8080/actuator/prometheus		Если 404 — endpoint не включён, используется другой путь или другой management path/port.
Есть нужные метрикиcurl ... | grep http_server_requestsЕсли метрики нет — приложение её не публикует или фильтрует.
Prometheus scrape pathmetrics_path: /actuator/prometheusЕсли путь неверный — target может быть up=0 или без нужных samples.
Порт managementmanagement.server.portActuator может жить на отдельном порту, отличном от порта приложения.
scrape_configs:
- job_name: payment-api
  metrics_path: /actuator/prometheus
  static_configs:
  - targets: ['payment-api:8080']
Важно: не публикуйте чувствительные Actuator endpoints наружу. Для мониторинга обычно нужен только endpoint Prometheus, доступный Prometheus внутри защищённой сети или кластера.

Что такое exporter

Exporter — процесс, который переводит состояние системы в формат Prometheus. Например, node_exporter отдаёт метрики Linux, postgres_exporter — PostgreSQL, redis_exporter — Redis.

ExporterЧто показываетПример метрикКогда смотреть
node_exporterCPU, RAM, disk, network.node_cpu_seconds_total, node_filesystem_avail_bytesПодозрение на нехватку ресурсов node/VM.
kube-state-metricsСостояние объектов Kubernetes.kube_pod_status_phase, kube_deployment_status_replicas_availablePod Pending, Deployment не выкатился, реплик меньше нужного.
application metricsБизнес- и техническое поведение приложения.http_requests_total, request_duration_seconds_bucketОшибки, latency, RPS, очереди, интеграции.
blackbox_exporterПроверки снаружи: HTTP, TCP, ICMP.probe_success, probe_duration_secondsПроверка доступности с точки зрения клиента.

3. Модель метрик и labels

Из чего состоит метрика

http_requests_total{job="payment-api",instance="10.1.2.3:8080",method="GET",code="200"} 15342
└ metric name       └ labels                                           └ value

В Prometheus отдельный временной ряд создаётся для каждой уникальной комбинации имени метрики и labels.

Labels: сила и риск

LabelХороший примерПлохой примерПочему
methodGET, POSTполный URL с query stringМетодов мало, URL с id создаст взрыв cardinality.
code200, 404, 500текст ошибкиКоды ограничены, текст ошибки почти бесконечен.
endpoint/api/payments/{id}/api/payments/123456Шаблон безопасен, конкретный id создаёт тысячи series.
podpayment-api-7c9d...request_idPod допустим для диагностики, request_id недопустим как label.
Cardinality — количество уникальных временных рядов. Слишком много series увеличивает память, диск, время запросов и риск деградации Prometheus.

Именование метрик

  • Счётчики обычно заканчиваются на _total: http_requests_total.
  • Длительности обычно содержат единицу: request_duration_seconds.
  • Размеры — _bytes: response_size_bytes.
  • Гистограммы создают серии _bucket, _sum, _count.

3.1 Типы метрик

Сравнение типов

ТипЧто означаетПримерТиповые функцииКогда использовать
CounterТолько растёт или сбрасывается при рестарте.http_requests_total, errors_totalrate, increase, irate, resetsКоличество событий: запросы, ошибки, ретраи, обработанные сообщения.
GaugeМожет расти и падать.queue_depth, memory_usage_bytesavg_over_time, max_over_time, delta, predict_linearТекущее состояние: память, размер очереди, активные сессии, температура.
HistogramРаспределение значений по buckets + sum/count.request_duration_seconds_buckethistogram_quantile, rate, sum by (le)Latency, размер ответа, длительность задач; нужен p95/p99 на серверной стороне.
SummaryКвантили считаются на стороне клиента.rpc_duration_seconds{quantile="0.99"}Обычно читают готовый quantile; rate для sum/countКогда нужны клиентские квантили и не требуется агрегация по многим инстансам.

Counter: пример

# Сколько запросов в секунду за последние 5 минут
sum(rate(http_requests_total[5m]))

# Доля ошибок 5xx
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
Используйте: rate() для графиков RPS и error rate; increase() для ответа «сколько событий произошло за период».

Gauge: пример

# Текущая глубина очереди
queue_depth{queue="payment-events"}

# Максимальная глубина очереди за 15 минут
max_over_time(queue_depth{queue="payment-events"}[15m])

# Прогноз заполнения диска через 4 часа
predict_linear(node_filesystem_avail_bytes[2h], 4 * 3600)
Используйте: Gauge для значений «сколько сейчас». Не применяйте rate() к обычному Gauge как к счётчику.

Histogram: пример p95 latency

histogram_quantile(
  0.95,
  sum by (le, service) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
Когда лучше Histogram: если нужно агрегировать latency по pod, instance, zone или service и считать p90/p95/p99 в Prometheus.

Summary: когда осторожно

Summary удобно показывает quantile на конкретном instance, но quantile нельзя корректно агрегировать обычным avg между pod. Поэтому для SLO и общих p95 по сервису чаще выбирают Histogram.

Типичная ошибка: avg(summary_metric{quantile="0.95"}) по pod не равен p95 сервиса.

4. Основы PromQL

Instant vector и range vector

Тип выраженияЧто возвращаетПримерКогда используется
Instant vectorТекущие значения series на момент времени.up{job="payment-api"}Статусы, таблицы, одиночные значения.
Range vectorНабор значений series за период.http_requests_total[5m]Функции rate, increase, avg_over_time.
ScalarОдно число.100Пороги, вычисления процентов.

Фильтрация labels

# Равно
http_requests_total{job="payment-api"}

# Не равно
http_requests_total{code!="200"}

# Регулярное выражение
http_requests_total{code=~"5..", method=~"GET|POST"}

# Не соответствует regex
http_requests_total{endpoint!~"/health|/metrics"}

Агрегации

# Сумма RPS по всем pod с сохранением service
sum by (service) (rate(http_requests_total[5m]))

# Убрать pod/instance, но оставить остальные labels
sum without (pod, instance) (rate(http_requests_total[5m]))

# Топ-5 endpoint по ошибкам
topk(5, sum by (endpoint) (rate(http_requests_total{code=~"5.."}[5m])))
Правило: сначала преобразуйте Counter через rate, потом агрегируйте: sum(rate(counter[5m])).

4.1 Функции PromQL: когда какую использовать

Функции для Counter

ФункцияЧто делаетКогда лучшеПример
rate(counter[5m])Средняя скорость роста в секунду.Графики RPS, error rate, стабильные алерты.sum(rate(http_requests_total[5m]))
irate(counter[1m])Мгновенная скорость по двум последним точкам.Быстрые всплески на графиках, не для шумных алертов.irate(node_cpu_seconds_total[1m])
increase(counter[1h])Сколько событий добавилось за период.Отчёт «сколько ошибок за час».increase(errors_total[1h])
resets(counter[1h])Сколько раз counter сбросился.Поиск рестартов/сбросов процесса.resets(process_cpu_seconds_total[1h])

Функции для Gauge

ФункцияЧто делаетКогда лучшеПример
avg_over_time(gauge[15m])Среднее значение за окно.Сгладить шум CPU, latency gauge, размер очереди.avg_over_time(queue_depth[15m])
max_over_time(gauge[15m])Максимум за окно.Поймать пики памяти, очереди, connection pool.max_over_time(jvm_memory_used_bytes[15m])

Функции для Histogram

# p99 latency по service

4.2 Готовые PromQL-рецепты для поддержки

HTTP-сервис

# RPS по сервисам
sum by (service) (rate(http_requests_total[5m]))

# Error rate 5xx в процентах
100 * sum(rate(http_requests_total{code=~"5.."}[5m]))
/ sum(rate(http_requests_total[5m]))

# p95 latency по endpoint
histogram_quantile(0.95,
  sum by (le, endpoint) (rate(http_request_duration_seconds_bucket[5m]))
)

# Топ endpoint по 5xx
topk(10, sum by (endpoint) (rate(http_requests_total{code=~"5.."}[5m])))

Kubernetes

# Pod не Ready
sum by (namespace, pod) (kube_pod_status_ready{condition="false"} == 1)

# Рестарты контейнеров за 15 минут
sum by (namespace, pod, container) (increase(kube_pod_container_status_restarts_total[15m]))

# Deployment: доступных реплик меньше желаемых
kube_deployment_spec_replicas - kube_deployment_status_replicas_available

# CPU usage pod
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))

Инфраструктура

# Использование CPU node
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

# Свободное место на filesystem
100 * node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
/ node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}

# Сетевые ошибки
rate(node_network_receive_errs_total[5m]) + rate(node_network_transmit_errs_total[5m])

Бизнес-метрики

# Успешные платежи в минуту
sum(rate(payment_success_total[5m])) * 60

# Доля отклонённых платежей
sum(rate(payment_declined_total[5m]))
/
sum(rate(payment_attempt_total[5m]))

# Задержка обработки очереди p95
histogram_quantile(0.95,
  sum by (le, queue) (rate(queue_processing_duration_seconds_bucket[5m]))
)
Хорошая бизнес-метрика должна отвечать на вопрос пользователя или процесса: платежи, заявки, сообщения, успешные операции, отказы.

5. Grafana

Что делает Grafana

Grafana визуализирует данные из Prometheus и других источников: строит панели, дашборды, переменные, transformations, thresholds и алерты. Для поддержки важны не номера версий, а рабочий процесс: найти источник данных, проверить PromQL, выбрать правильную панель, настроить единицы, thresholds, transformations и алерты.

Из чего состоит дашборд

ЭлементЗадачаПример
Data sourceИсточник данных.Prometheus prod, Loki, Elasticsearch.
PanelВизуализация одного или нескольких запросов.Time series для RPS, Stat для статуса.
VariableФильтр дашборда.$namespace, $service, $pod.
TransformationПреобразование результата перед показом.Join, Labels to fields, Organize fields.
Field optionsЕдиницы, decimals, thresholds, mappings.ms, %, req/s, зелёный/жёлтый/красный.

Transformations: что это и когда использовать

Transform в Grafana — это преобразование результата запроса перед отображением на панели. Transform не меняет данные в Prometheus и не заменяет PromQL, а только помогает подготовить данные к визуализации: переименовать поля, объединить несколько запросов, скрыть лишние колонки, посчитать поле или развернуть labels в таблицу.

TransformКогда полезенПример для поддержки
Organize fieldsУбрать лишние колонки, переименовать поля, изменить порядок.В таблице targets оставить только ris_code, job, instance, up.

Правило: если расчёт нужен для алерта или должен быть единым для всех дашбордов — лучше делать его в PromQL или recording rule. Если нужно только красиво подготовить таблицу или подписи на панели — используйте Transform.

Базовый workflow создания панели

1. Выбрать data source
Обычно Prometheus для метрик.
2. Написать PromQL
Проверить результат в Explore или Query inspector.

3. Выбрать визуализацию

4. Настроить единицы и thresholds
Например, проценты для error rate, milliseconds для latency.

5.2 Transform в Grafana

Зачем нужны Transform

Transformations применяются после выполнения запроса к data source и до вывода результата на панель. Для прикладной поддержки это особенно полезно в таблицах, светофорах и обзорных дашбордах, где нужно показать не «сырой» временной ряд, а понятный список систем, статусов и отклонений.

Аналогия: PromQL достаёт и считает данные, а Transform приводит результат к форме отчёта: переименовывает колонки, объединяет таблицы, оставляет нужные поля и подсвечивает важное.

Типовые сценарии

СценарийКак сделатьПример
Сделать таблицу ИСЗапрос Prometheus → Labels to fields → Organize fields.max by (ris_code, job) (up)
Светофор по сервисамЗапросы availability/error/latency → Join by field → Thresholds/value mappings.Зелёный: OK, жёлтый: degradation, красный: incident.
Показать последнее состояниеReduce: Last not null.Последний статус target, pod или blackbox-проверки.
Скрыть технические поляOrganize fields.Убрать Time, __name__, лишние labels.
Посчитать поле в панелиAdd field from calculation.Success % = success / total * 100.

Пример: таблица доступности ИС по ris_code

Запрос возвращает состояние targets в разрезе информационных систем:

max by (ris_code, job) (up{ris_code!=""})
  1. Panel: Table.
  2. Transform: Labels to fields, чтобы ris_code стал колонкой.
  3. Transform: Organize fields, оставить ris_code, job, Value.
  4. Value mappings: 1 → OK, 0 → DOWN.
  5. Thresholds: зелёный для 1, красный для 0.
Частая ошибка: пытаться через Transform исправить неправильный PromQL. Если series слишком много, labels не те или агрегация неверная — сначала исправьте запрос, иначе панель будет красивой, но misleading.

5.3 Проектирование дашбордов поддержки

Структура хорошего прикладного дашборда

  1. Верхний ряд: здоровье сервиса — availability, error rate, p95/p99 latency, RPS.
  2. Второй ряд: разрезы — endpoints, status codes, методы, consumer groups, очереди.
  3. Третий ряд: инфраструктура — pod restarts, CPU/RAM, throttling, GC, DB pool.
  4. Нижний ряд: диагностика — таблицы top offenders, down targets, recent deploy annotations.

Variables

# namespace variable
label_values(kube_namespace_status_phase, namespace)

# service variable
label_values(http_requests_total{namespace="$namespace"}, service)

# pod variable
label_values(up{namespace="$namespace", service="$service"}, pod)
Для поддержки: variables экономят время: один дашборд работает для dev/test/prod и разных сервисов.

Thresholds и units

МетрикаUnitThreshold примерКомментарий

Latencyseconds / millisecondsжёлтый > 300ms, красный > 1sНе смешивайте секунды и миллисекунды.
Disk usagepercentжёлтый > 80%, красный > 90%Дополнить прогнозом predict_linear.

Антипаттерн: дашборд «всё обо всём» с 80 панелями. В инциденте он замедляет расследование. Лучше несколько дашбордов: обзор, HTTP, Kubernetes, БД/очереди, бизнес.

5.4 Золотые сигналы SRE для прикладной поддержки

Зачем поддержке золотые сигналы

Золотые сигналы — это минимальный набор метрик, который помогает быстро понять состояние сервиса: он доступен, насколько быстро отвечает, сколько запросов обрабатывает и не упирается ли в лимиты.

Главная идея: в инциденте не надо сразу смотреть 50 графиков. Сначала проверьте четыре сигнала: Latency, Traffic, Errors, Saturation.

Четыре сигнала

СигналЧто показываетТиповой вопрос поддержкиПанель Grafana
LatencyСкорость ответа сервиса: p95, p99, среднее.Сервис отвечает медленно или нормально?Time series, Stat
TrafficКоличество запросов: RPS, запросы по endpoint, методам, ИС.Есть ли нагрузка, всплеск или провал трафика?Time series, Bar gauge
ErrorsДоля ошибок: 4xx, 5xx, неуспешные операции.Пользователи получают ошибки?Stat, Time series, Table
SaturationНасыщение ресурсов: CPU, RAM, thread pool, DB pool, очереди.Сервис близок к пределу?Gauge, Bar gauge, Table

PromQL-примеры по ris_code

# Traffic: RPS по информационным системам
sum by (ris_code) (rate(http_requests_total{ris_code!=""}[5m]))

# Errors: процент 5xx по ИС
100 *
sum by (ris_code) (rate(http_requests_total{ris_code!="",code=~"5.."}[5m]))
/
sum by (ris_code) (rate(http_requests_total{ris_code!=""}[5m]))

# Latency: p95 по ИС
histogram_quantile(
  0.95,
  sum by (ris_code, le) (rate(http_request_duration_seconds_bucket{ris_code!=""}[5m]))
)

# Saturation: рестарты контейнеров за 15 минут
sum by (ris_code) (increase(kube_pod_container_status_restarts_total{ris_code!=""}[15m]))
Проверьте имена метрик: в Spring Boot часто встречаются http_server_requests_seconds_count и http_server_requests_seconds_bucket, а в других приложениях — http_requests_total и http_request_duration_seconds_bucket.

5.5 Переменные Grafana

Что такое variable

Переменные Grafana позволяют сделать один универсальный dashboard для разных ИС, namespace, сервисов, pod и окружений. Пользователь выбирает значение в выпадающем списке, а Grafana подставляет его в PromQL.

Для сопровождения: вместо десяти одинаковых dashboard по разным ИС лучше сделать один dashboard с переменной $ris_code.

Базовый набор переменных

ПеременнаяЗачем нужнаПример query
$ris_codeВыбор информационной системы.label_values(up, ris_code)
$namespaceВыбор Kubernetes namespace.label_values(up{ris_code="$ris_code"}, namespace)
$serviceВыбор сервиса/приложения.label_values(up{ris_code="$ris_code",namespace="$namespace"}, service)
$podДиагностика конкретного pod.label_values(up{ris_code="$ris_code",namespace="$namespace"}, pod)
$intervalОкно агрегации для rate/increase.5m, 15m, 1h

Как использовать переменные в PromQL

# RPS выбранной ИС
sum(rate(http_requests_total{ris_code="$ris_code"}[$interval]))

# 5xx выбранной ИС по endpoint
sum by (endpoint) (
  rate(http_requests_total{ris_code="$ris_code",code=~"5.."}[$interval])
)

# p95 latency выбранной ИС
histogram_quantile(
  0.95,
  sum by (le, endpoint) (
    rate(http_request_duration_seconds_bucket{ris_code="$ris_code"}[$interval])
  )
)
Осторожно с All: если включить значение All, запрос может стать тяжёлым. Для больших окружений лучше ограничивать список namespace/ris_code или использовать regex аккуратно.

Практический порядок настройки

  1. Dashboard settings → Variables → New variable.
  2. Type: Query, Data source: Prometheus.
  3. Name: ris_code.
  4. Query: label_values(up, ris_code).
  5. Включите Refresh: On dashboard load.
  6. Повторите для namespace, service, pod.

5.6 Типовые инциденты по метрикам

Как читать инцидент через метрики

Метрики помогают быстро отделить прикладную ошибку от инфраструктурной, массовую проблему от локальной, деградацию производительности от полной недоступности.

Правило: сначала определите масштаб — одна ИС, один namespace, один pod, один endpoint или весь контур.

5.7 Типичные ошибки PromQL и Cardinality

Ошибки, которые чаще всего ломают графики

ОшибкаПочему плохоКак правильно
Используют rate() для gaugerate() нужен для counter, который только растёт.Для gauge использовать avg_over_time, max_over_time, min_over_time.
Строят процент без одинаковой группировкиPrometheus не сможет корректно сопоставить числитель и знаменатель.Одинаковые by (...) в обеих частях выражения.
Берут слишком маленькое окно [1m]График шумит, особенно при редком scrape.Начать с [5m] или [10m].
Не фильтруют статусыНельзя понять, что именно растёт: 2xx, 4xx или 5xx.Использовать status=~"5..", status="200".
Группируют по слишком многим labelsDashboard становится тяжёлым, график нечитаемым.Оставлять только важные labels: ris_code, status, method.
Сравнивают instant-значение без окнаМожно поймать случайный всплеск.Для алертов использовать окно и условие for.

Пример: процент 5xx

Неправильно: числитель сгруппирован по ris_code, а знаменатель — по status. Результат может быть пустым или некорректным.

# Плохо

/
sum(rate(http_server_requests_seconds_count[5m])) by (status)

Правильно: одинаковая группировка в числителе и знаменателе.

# Хорошо
100 *
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (ris_code)
/
sum(rate(http_server_requests_seconds_count[5m])) by (ris_code)

Как выбирать окно для rate

СитуацияРекомендуемое окноПочему
Быстрая диагностика[5m]Хороший баланс между скоростью реакции и шумом.
Низкий трафик[10m] или [15m]На малом числе запросов короткое окно даёт скачки.
Отчёт за сутки[30m] или агрегация по большому периодуНужен сглаженный тренд, а не секундные всплески.

Что такое cardinality

Cardinality — это количество уникальных временных рядов, которые создаёт метрика из-за комбинаций labels.

Одна метрика с большим количеством уникальных label-значений может породить тысячи или миллионы рядов. Это увеличивает нагрузку на Prometheus, замедляет запросы и делает dashboard тяжёлым.

Простая формула: временные ряды = имя метрики × все комбинации labels.

Хорошие и плохие labels

LabelОценкаПочему
ris_codeХорошоОграниченный справочник информационных систем.
statusХорошоОграниченное число HTTP-статусов.
methodХорошоGET, POST, PUT, DELETE — мало значений.
uri с шаблоном /orders/{id}ХорошоШаблон не создаёт ряд на каждый заказ.
user_idПлохоУникальное значение на пользователя.
request_idПлохоУникальное значение на запрос.
session_idПлохоМожет создать огромное количество рядов.

Пример

# Плохо: каждый user_id создаёт новые ряды
http_requests_total{ris_code="PAY", user_id="12345", status="200"}

# Хорошо: labels стабильны и имеют ограниченное число значений
http_requests_total{ris_code="PAY", endpoint="/api/payments", status="200"}

Как поддержке заметить проблему cardinality

# Сколько рядов есть по каждой метрике
count by (__name__) ({ris_code="PAY"})

# Какие labels создают много комбинаций
count by (ris_code, uri, status) (http_server_requests_seconds_count)

# Топ uri по количеству рядов
sort_desc(count by (uri) (http_server_requests_seconds_count))
Правило: в labels нельзя выносить персональные, уникальные и бесконечно растущие значения: телефон, счёт, ФИО, request_id, session_id, trace_id.

6. SLI / SLO / SLA простыми словами

Зачем это прикладной поддержке

SLI, SLO и SLA помогают переводить технические метрики в язык качества сервиса: насколько система доступна, насколько быстро отвечает и когда нарушение действительно критично для бизнеса.

Главная идея: не каждый всплеск ошибки — авария. Аварией становится устойчивое нарушение согласованного уровня качества.
ТерминЧто означаетПример для ИСЧто делает поддержка
SLIService Level Indicator — показатель, который измеряем.Процент успешных HTTP-ответов, p95 latency, доступность scrape.Строит метрику и проверяет фактическое значение.
SLOService Level Objective — целевой уровень качества.99.5% успешных запросов за сутки, p95 меньше 2 секунд.Смотрит, нарушена ли цель и как долго.
SLAService Level Agreement — обязательство перед заказчиком.Доступность ИС не ниже 99% в месяц.Фиксирует факт нарушения и передаёт корректные данные.

Примеры SLI на PromQL

SLI обычно строят как процент хороших событий от общего количества событий.

# Процент успешных 2xx-ответов по ИС
100 *
sum(rate(http_server_requests_seconds_count{status=~"2.."}[5m])) by (ris_code)
/
sum(rate(http_server_requests_seconds_count[5m])) by (ris_code)
# p95 latency по ИС
histogram_quantile(
  0.95,
  sum(rate(http_server_requests_seconds_bucket[5m])) by (le, ris_code)
)
Важно: SLI должен быть понятным и устойчивым. Например, "процент 2xx" хорош для доступности, а "p95 latency" — для производительности.

Как читать нарушение SLO

СитуацияКак интерпретироватьДействие
2xx = 99.9%, SLO = 99.5%Цель выполняется.Наблюдать, инцидент не заводить.
2xx = 96%, SLO = 99.5% в течение 2 минутКраткий всплеск, нужно подтвердить устойчивость.Проверить график за 15–30 минут.
2xx = 96%, SLO = 99.5% в течение 20 минутУстойчивое нарушение.Запустить runbook, собрать факты, эскалировать.
p95 latency выше SLO, но 5xx нетПроблема производительности, а не полной недоступности.Проверить saturation: CPU, memory, DB pool, очереди.

7. Алерты и правила

Alerting rule: пример

groups:
- name: payment-api
  rules:
  - alert: PaymentApiHighErrorRate
    expr: |
      100 * sum(rate(http_requests_total{service="payment-api",code=~"5.."}[5m]))
      / sum(rate(http_requests_total{service="payment-api"}[5m])) > 5
    for: 10m
    labels:
      severity: critical
      team: payments
    annotations:
      summary: "High 5xx error rate in payment-api"
      description: "5xx error rate is above 5% for 10 minutes."

Recording rules

Recording rule заранее считает тяжёлый или часто используемый запрос и сохраняет результат как новую метрику.

- record: job:http_requests:rate5m
  expr: sum by (job) (rate(http_requests_total[5m]))
Когда использовать: сложные p95, error rate и агрегаты, которые нужны на многих панелях или в алертах.

Как делать алерты полезными

ПравилоПочемуПример
Алерт должен быть пригодным для действияДежурный должен понимать, что делать.«Payment API 5xx > 5% 10m», а не «metric high».
Используйте forЗащищает от секундных всплесков.for: 10m
Разделяйте warning/criticalНе всё требует ночного звонка.warning > 1%, critical > 5%.

7.1 Runbook при срабатывании алерта

Цель runbook

Runbook — это инструкция, что делает поддержка после уведомления. Хороший runbook уменьшает время реакции и помогает передать разработке не эмоции, а факты.

Универсальный порядок действий

1. Подтвердить алерт
Откройте dashboard/Explore и проверьте, что условие действительно выполняется сейчас или выполнялось в указанном периоде.
2. Определить масштаб
Одна ИС, несколько ИС, один namespace, один pod, один endpoint или массовая проблема?
count by (ris_code) (up{ris_code!=""} == 0)
3. Проверить золотые сигналы
Latency, Traffic, Errors, Saturation.
4. Сравнить с изменениями
Был ли релиз, переключение маршрутов, изменение конфигурации, рост нагрузки?
5. Локализовать источник
Разрез по endpoint, pod, instance, status, namespace, version.
6. Принять действие или эскалировать
Если причина инфраструктурная — передать платформе. Если прикладная — разработке. Если массовая — координатору инцидента.

Шаблон сообщения по алерту

Период: 14:05–14:20
Текущее значение: 8.7% 5xx
Норма / threshold: critical > 5% for 10m
Затронутые endpoints: /api/orders/create, /api/orders/pay
RPS: без роста / вырос с 20 до 120
Latency p95: 0.4s → 2.8s
Pods: 2 рестарта за 15 минут / рестартов нет
Свежие изменения: релиз 1.8.4 в 13:55 / изменений не найдено
Вывод поддержки: похоже на прикладную деградацию после релиза, нужна проверка логов по endpoint.

Симптомы и первые проверки

СимптомВозможная причинаПервая проверка
В Grafana нет данныхНеверный PromQL, time range, data source, target down.Explore → тот же запрос; Prometheus → Status → Targets.
Алерт не сработалНет series, неверный label, условие не держалось for.Выполнить expr в Prometheus на нужном time range.

Плейбук: Grafana показывает N/A

1. Проверить time range
N/A может быть из-за выбранного периода без данных.
2. Открыть Explore
Выполнить PromQL отдельно, без transformations панели.
3. Проверить labels
Убедиться, что переменные $namespace, $service подставляются корректно.
4. Проверить target
В Prometheus посмотреть Status → Targets и метрику up.
up{job="payment-api"}
5. Проверить scrape
Ошибки HTTP, timeout, TLS, auth, неверный metrics_path или слишком долгий endpoint метрик.
scrape_duration_seconds{job="payment-api"}
scrape_samples_scraped{job="payment-api"}

Плейбук: резкий рост 5xx

1. Подтвердить симптом
100 * sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))
2. Найти источник
topk(10, sum by (service, endpoint, code) (rate(http_requests_total{code=~"5.."}[5m])))
3. Сравнить latency и нагрузку
sum(rate(http_requests_total[5m]))
histogram_quantile(0.95, sum by (le, service) (rate(http_request_duration_seconds_bucket[5m])))
4. Проверить Kubernetes состояние
increase(kube_pod_container_status_restarts_total[15m])
kube_deployment_spec_replicas - kube_deployment_status_replicas_available
5. Перейти в логи/трейсы
Метрики показывают масштаб, логи и трейсы уточняют конкретную причину.

Вопросы

Прогресс: 0/15 правильных ответов

1. Какая модель сбора обычно используется Prometheus?

Разбор: Prometheus обычно сам ходит на endpoint метрик по scrape_interval. Это может быть /metrics, /prometheus или /actuator/prometheus.

2. Что означает метрика up == 0?

Разбор: up отражает успех scrape target.

3. Какой тип метрики только растёт или сбрасывается?

Разбор: Counter подходит для запросов, ошибок, событий.

4. Какую функцию чаще использовать для RPS?

Разбор: rate(counter[5m]) даёт среднюю скорость роста в секунду.

5. Что опасно помещать в label?

Разбор: request_id/user_id создают высокую cardinality.

6. Как считать p95 latency по histogram?

Разбор: для classic histogram нужен rate по buckets и агрегация с label le.

7. Почему нельзя усреднять summary quantile по pod?

Разбор: для агрегируемых p95/p99 обычно используют histogram.

8. Какая панель лучше для RPS во времени?

Разбор: RPS — временной ряд, поэтому Time series.

9. Какая панель лучше для списка top-10 endpoints по 5xx?

Разбор: таблица удобна для сортируемых списков проблем.

10. Зачем нужны recording rules?

Разбор: recording rules ускоряют панели и упрощают алерты.

11. Что делает параметр for в алерте?

Разбор: for снижает шум от кратковременных всплесков.

12. Что первым проверить, если в Grafana N/A?

Разбор: сначала отделяем проблему запроса/диапазона от проблемы данных.

13. Какая функция подходит для прогноза заполнения диска?

Разбор: predict_linear применяют к gauge для линейного прогноза.

14. Почему запрос может быть медленным?

Разбор: нагрузку создают объём series и сложность вычислений.

15. Что лучше показывает состояние Ready/NotReady по pod во времени?

Разбор: State timeline показывает смену дискретных состояний во времени.

Выбор функции

  • rate — стабильная скорость Counter для графиков и алертов.
  • irate — резкие всплески на графике, осторожно с алертами.
  • increase — сколько событий произошло за период.
  • avg_over_time — сгладить Gauge.
  • max_over_time — поймать пик Gauge.
  • histogram_quantile — p90/p95/p99 из Histogram.
  • predict_linear — прогноз по Gauge, например диск.

Выбор панели Grafana

  • Time series — всё, что меняется во времени.
  • Stat — одно ключевое значение.
  • Gauge — значение в известном диапазоне.
  • Bar gauge — сравнение нескольких объектов сейчас.
  • Table — топы, списки, проблемные объекты.
  • Heatmap — распределения.
  • State timeline — состояния во времени.
