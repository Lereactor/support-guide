2. Потоки Java

Что такое Thread в Java

Thread, или поток, — это дискретная единица многопоточности, управляемая Java Virtual Machine. Поток выполняет участок кода независимо от других потоков внутри одного Java-процесса.

В большинстве production JVM поток Java соответствует потоку операционной системы — native thread. То есть JVM управляет Java-потоками на своём уровне, но фактическое выполнение кода обеспечивается потоками ОС.

Java application ↓ создаёт Thread / Executor task JVM Thread ↓ отображается на OS native thread ↓ выполняется на CPU core / scheduler OS
Для поддержки: если потоков слишком много, это влияет не только на JVM, но и на операционную систему: растёт расход памяти на стеки, переключение контекста и нагрузка на scheduler.

Идентификатор, имя и тип потока

У каждого потока есть уникальный идентификатор и имя. Имя потока особенно важно при анализе thread dump: по нему можно понять, к какой подсистеме относится поток — HTTP worker, scheduler, Kafka consumer, Hikari housekeeper, GC thread или custom executor.

Daemon и non-daemon потоки

Потоки в Java могут быть daemon и non-daemon.

  • Non-daemon — обычные рабочие потоки. Пока хотя бы один non-daemon поток продолжает работу, JVM не завершает процесс штатно.
  • Daemon — фоновые служебные потоки. Их работа не удерживает JVM от завершения.

Программа завершает работу, когда завершены все non-daemon потоки или когда явно вызывается завершение процесса, например через Runtime.exit / System.exit. Работающие daemon-потоки не мешают завершению JVM.

Практическая формулировка: JVM ждёт завершения non-daemon потоков, но не ждёт daemon-потоки. Поэтому ошибка в жизненном цикле non-daemon executor может мешать корректному shutdown приложения.

Состояния потоков: что видно в thread dump

Поток может находиться в одном из нескольких состояний. Для поддержки важно не просто увидеть состояние, а понять, нормально ли оно для конкретного типа потока.

Уточнение: если поток вызвал wait с таймаутом и таймаут истёк, он больше не считается ожидающим по этой причине — он продолжит борьбу за выполнение или перейдёт в другое состояние.

Sleeping thread

Sleeping thread, или «спящий» поток, — это поток, который временно не выполняется, потому что вызвал Thread.sleep(...) на заданную длительность.

В thread dump такой поток обычно будет в состоянии TIMED_WAITING. Сам по себе sleeping не является ошибкой: это нормальный механизм паузы для scheduler, retry, polling или backoff-логики.

Когда подозрительно: если большое число рабочих HTTP-потоков находится в sleep, это может означать неправильную retry-логику внутри обработки пользовательского запроса.

Monitor и synchronized

Monitor — механизм JVM для синхронизации доступа нескольких потоков к одному объекту. В Java он используется через ключевое слово synchronized.

Каждый объект в Java имеет связанный с ним monitor. Когда поток входит в блок synchronized, он захватывает monitor объекта. Пока поток владеет monitor, другой поток не может войти в synchronized-блок, защищённый тем же объектом.

private final Object lock = new Object();

public void updateState() {
    synchronized (lock) {
        // Только один поток одновременно может выполнять этот блок
        // Остальные будут BLOCKED на monitor объекта lock
    }
}
Поток A вошёл в synchronized(lock) ↓ Поток A владеет monitor объекта lock ↓ Поток B пытается войти в synchronized(lock) ↓ Поток B переходит в BLOCKED ↓ Поток A выходит из synchronized ↓ Monitor освобождается, один из ожидающих потоков продолжает работу
Для поддержки: если в thread dump много потоков BLOCKED на одном monitor, нужно найти поток-владелец блокировки и его stack trace.

wait, notify и notifyAll

Методы wait, notify и notifyAll используются для координации потоков через monitor объекта.

  • wait() — поток освобождает monitor и ждёт уведомления.
  • wait(timeout) — поток ждёт уведомления или истечения таймаута.
  • notify() — будит один ожидающий поток.
  • notifyAll() — будит все потоки, ожидающие на этом объекте.
Важно: поток в WAITING не всегда «завис». Он может штатно ждать событие из очереди, пула, scheduler или другого потока. Проблема начинается, когда ожидание мешает полезной работе сервиса.

Deadlock: взаимная блокировка

Deadlock — ситуация, когда два или более потока навсегда ждут друг друга. Например, поток A удерживает ресурс 1 и ждёт ресурс 2, а поток B удерживает ресурс 2 и ждёт ресурс 1. Ни один из них не может продолжить работу.

Thread A захватил Lock 1 Thread B захватил Lock 2 Thread A ждёт Lock 2 Thread B ждёт Lock 1 Оба потока ждут друг друга Полезная работа не выполняется

Во взаимной блокировке может участвовать больше двух потоков. В thread dump JVM часто явно показывает блок Found one Java-level deadlock.

Признак deadlockЧто делать поддержке
В thread dump есть Found one Java-level deadlockСрочно приложить dump и эскалировать разработке.
Потоки в BLOCKED ждут locks друг другаСнять 2–3 thread dump для подтверждения.
Сервис не делает прогресс, но процесс живПроверить liveness/readiness, latency, thread dump.
Важно: рестарт может временно снять deadlock, но не исправит дефект синхронизации. Перед рестартом, если возможно, соберите thread dump.

Livelock: активность есть, прогресса нет

Livelock — ситуация, когда потоки не заблокированы формально и продолжают выполнять действия, но эти действия мешают друг другу и не приводят к полезному результату.

Это похоже на собаку, которая бегает за своим хвостом: движение есть, но прогресса нет. В отличие от deadlock, при livelock потоки могут оставаться активными, менять состояние, потреблять CPU, но бизнес-операция не завершается.

Thread A реагирует на действие Thread B ↓ Thread B реагирует на действие Thread A ↓ Thread A снова возвращается к исходному действию ↓ Цикл повторяется ↓ CPU может тратиться, но полезная работа не завершается

2.1 Мониторинг потоков в Kubernetes и Grafana

Зачем мониторить потоки в Kubernetes

В Java-микросервисе поток — это не только объект JVM. Обычно Java thread соответствует native thread операционной системы внутри контейнера. Поэтому большое количество потоков влияет сразу на несколько уровней: JVM, контейнер, Kubernetes node и пользовательскую latency.

Java Thread ↓ OS native thread внутри контейнера ↓ потребляет память на stack: -Xss ↓ конкурирует за CPU container limit ↓ может усиливать CPU throttling, latency, readiness/liveness failures
Главный вывод: много потоков — это больше памяти на thread stacks, больше переключений контекста и выше риск упереться в CPU limit контейнера.

Kubernetes-команды рядом с Grafana

Grafana показывает тренд и масштаб, но для расследования нужны факты из Kubernetes: restarts, node, limits, probes, events и логи контейнера.

# Проверить pod, node, restarts
kubectl get pod -n <namespace> -o wide

# Проверить events, probes, limits, last state
kubectl describe pod -n <namespace> <pod>

# Проверить ресурсы контейнера
kubectl top pod -n <namespace> <pod> --containers

# Логи текущего контейнера
kubectl logs -n <namespace> <pod> --tail=300

# Логи предыдущего контейнера после рестарта
kubectl logs -n <namespace> <pod> --previous --tail=300

# Проверить фактические JVM flags, включая -Xss
kubectl exec -n <namespace> <pod> -- sh -c 'jcmd 1 VM.flags'

# Проверить число потоков через JVM
kubectl exec -n <namespace> <pod> -- sh -c 'jcmd 1 Thread.print | grep -c "java.lang.Thread.State"'
Важно: если pod уже рестартовал, thread dump старого процесса снять нельзя. Тогда используйте previous logs, Kubernetes events и Grafana-графики до момента рестарта.

3. Heap и Non-Heap

Что такое heap простыми словами

Всякий раз, когда Java-приложение создаёт объект, этот объект размещается в области памяти JVM, которая называется heap, или куча. В heap попадают DTO, строки, коллекции, результаты SQL-запросов, JSON/XML-объекты, кэши, доменные сущности и большинство временных объектов, которые возникают при обработке запросов.

Объём heap ограничен настройками JVM и лимитами контейнера. Поэтому JVM нужен механизм, который освобождает место. Этим занимается Garbage Collector: он ищет объекты, которые больше недостижимы из живых ссылок, и освобождает занимаемую ими память.

HTTP-запрос ↓ Java-код создаёт объекты ↓ Объекты размещаются в Heap ↓ Garbage Collector ищет недостижимые объекты ↓ Недостижимые объекты удаляются ↓ В heap снова появляется свободное место
Главная идея: heap — это рабочая область для Java-объектов, а GC — механизм, который пытается поддерживать в этой области свободное место.

Что будет, если heap закончится

Если свободное место в heap израсходовано, а Garbage Collector не может освободить достаточно памяти, JVM получает ошибку:

Exception in thread "main" java.lang.OutOfMemoryError: Java heap space

В production это может проявляться не только как ошибка в логах. Возможны рост latency, частые Full GC, отказ readiness/liveness probes, падение контейнера, рестарт pod или статус OOMKilled, если контейнер превысил memory limit Kubernetes.

СимптомЧто означаетЧто проверить
java.lang.OutOfMemoryError: Java heap spaceJVM не смогла выделить объект в heap.Heap used/max, old gen, GC, heap dump.
Частые Full GCJVM пытается освободить старую область.Old Gen, live data, GC pause, allocation rate.
Latency растёт перед падениемПотоки приложения тормозят из-за GC или нехватки памяти.p95/p99 latency рядом с GC pause.
Pod OOMKilledKubernetes убил контейнер за превышение memory limit.Container memory, heap, non-heap, direct memory, thread stacks.

Почему GC не всегда спасает

Garbage Collector удаляет только те объекты, которые больше недостижимы, то есть на них нет живых ссылок из работающего приложения. Но иногда объект уже не нужен бизнес-логике, однако ссылка на него всё ещё где-то хранится. Для GC такой объект выглядит живым, поэтому он не будет удалён.

Объект больше не нужен приложению ↓ Но ссылка на него осталась в cache / static map / ThreadLocal / очереди ↓ GC считает объект живым ↓ Объект не удаляется ↓ Heap постепенно заполняется ↓ Возникает memory leak
Ключевой момент: утечка памяти в Java — это не обязательно «потерянный» объект. Чаще это объект, на который всё ещё есть ссылка, но приложение уже не должно было его хранить.

Карта памяти JVM в контейнере

Важно помнить: heap — только часть памяти контейнера. Kubernetes ограничивает всю память контейнера, а не только heap. Поэтому сервис может быть убит по memory limit даже тогда, когда heap ещё не достиг -Xmx.

Container memory limit ├─ Java Heap (-Xmx / MaxRAMPercentage) │ ├─ Young Generation │ │ ├─ Eden │ │ ├─ Survivor S0 │ │ └─ Survivor S1 │ └─ Old Generation ├─ Non-Heap │ ├─ Metaspace │ ├─ Compressed Class Space │ └─ Code Cache ├─ Direct / off-heap buffers ├─ Thread stacks (-Xss × number of threads) ├─ GC / JVM native structures └─ Native libraries and OS overhead
Контейнерный риск: нельзя бездумно ставить -Xmx равным memory limit контейнера. Кроме heap есть non-heap, direct memory, стеки потоков и native overhead.

Из чего состоит Heap

Что делать поддержке, если heap переполнен, но сервис ещё живёт в Kubernetes

1. Не перезапускать pod сразу
Рестарт может временно помочь, но уничтожит состояние, по которому можно найти причину. Если сервис ещё отвечает и есть время — сначала соберите факты.
2. Зафиксировать масштаб
Проверьте, проблема на одном pod или на всех replicas. Сравните heap, restarts, version/image, node.
kubectl get pod -n <namespace> -o wide
kubectl describe pod -n <namespace> <pod>
3. Проверить графики памяти
Откройте heap used/max, old gen, GC pause, Full GC count, container memory, thread count, RPS и latency в одном временном окне.
4. Проверить логи на OOM и GC-признаки
Ищите OutOfMemoryError, Java heap space, частые timeout, readiness/liveness failures.
kubectl logs -n <namespace> <pod> --tail=500 | egrep -i "outofmemory|java heap space|gc overhead|killed|readiness|liveness"
5. Проверить свободное место перед heap dump
Heap dump может быть большим. Если места нет, можно уронить контейнер или забить ephemeral storage.
kubectl exec -n <namespace> <pod> -- sh -c 'df -h /tmp / || true'
6. Снять heap dump
Если runbook разрешает и место есть, снимите heap dump, скопируйте его и удалите из контейнера.
kubectl exec -n <namespace> <pod> -- sh -c 'jcmd 1 GC.heap_dump /tmp/heap.hprof'
kubectl cp <namespace>/<pod>:/tmp/heap.hprof ./heap.hprof
kubectl exec -n <namespace> <pod> -- rm -f /tmp/heap.hprof
7. Параллельно снять JFR, если проблема развивается
JFR поможет увидеть allocation pressure, GC, CPU и горячие участки кода.
kubectl exec -n <namespace> <pod> -- sh -c '
  jcmd 1 JFR.start name=heap-pressure settings=profile duration=5m filename=/tmp/heap-pressure.jfr
'
kubectl cp <namespace>/<pod>:/tmp/heap-pressure.jfr ./heap-pressure.jfr
8. Снизить влияние на пользователей
По регламенту: временно вывести pod из нагрузки, увеличить replicas, сделать rollback, ограничить batch/job, отключить проблемный трафик или согласовать временное увеличение memory limit.
9. Эскалировать с полным пакетом фактов
Передайте разработке heap dump/JFR, графики, время начала, pod, image tag, нагрузку, последние релизы и логи.

Как конфигурировать Java heap и non-heap в Kubernetes

В Kubernetes память Java-сервиса нужно настраивать не только через resources.limits.memory, но и через JVM-флаги. Kubernetes ограничивает память контейнера целиком, а JVM внутри этого лимита должна разместить heap, metaspace, compressed class space, code cache, direct memory, стеки потоков и native overhead.

Главный принцип: сумма JVM-областей должна быть меньше memory limit контейнера. Нужно оставлять запас под native memory, JVM overhead, libc, SSL, DNS, драйверы, monitoring-agent и временные пики.

Пример JVM options через переменные окружения

Один из практичных подходов — вынести размеры областей памяти в переменные окружения и собирать JAVA_TOOL_OPTIONS или JAVA_OPTS при старте контейнера.

-Xms${HEAP_SIZE_MB}M \
-Xmx${HEAP_SIZE_MB}M \
-Xss1M \
-XX:MaxMetaspaceSize=${METASPACE_SIZE_MB}M \
-XX:CompressedClassSpaceSize=${COMPRESSED_CLASS_SPACE_SIZE_MB}M \
-XX:ReservedCodeCacheSize=${RESERVED_CODE_CACHE_SIZE_MB}M \
-XX:MaxDirectMemorySize=${DIRECT_MEMORY_SIZE_MB}M
ФлагЧто задаётКомментарий для поддержки
-XmsНачальный размер heap.Если -Xms равен -Xmx, JVM сразу резервирует стабильный размер heap. Это снижает динамическое расширение heap, но требует корректного расчёта memory limit.
-XmxМаксимальный размер heap.Главный лимит Java heap. Если heap заполнен и GC не помогает — возможен Java heap space.
-XssРазмер стека одного потока.Память на стеки считается примерно как thread_count × Xss. При большом числе потоков это заметная часть container memory.
-XX:MaxMetaspaceSizeМаксимальный размер Metaspace.Ограничивает метаданные классов. При нехватке возможен OutOfMemoryError: Metaspace.
-XX:CompressedClassSpaceSizeРазмер области compressed class space.Связана с metadata классов. Обычно меняется реже, но важна при большом числе классов.
-XX:ReservedCodeCacheSizeРазмер Code Cache для JIT-кода.Если code cache заполнится, JIT может деградировать, что влияет на производительность.
-XX:MaxDirectMemorySizeЛимит direct/off-heap memory.Важен для Netty, NIO, драйверов, буферов. Если heap стабилен, а container memory растёт — смотреть сюда.

Пример Deployment с настройкой памяти JVM

Ниже пример, как это может выглядеть в Kubernetes Deployment. Значения приведены как шаблон, их нельзя копировать в production без расчёта под конкретный сервис.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: payment-api
        image: registry.example.ru/payment-api:1.0.0
        resources:
          requests:
            memory: "1536Mi"
            cpu: "500m"
          limits:
            memory: "2048Mi"
            cpu: "1000m"
        env:
        - name: HEAP_SIZE_MB
          value: "1024"
        - name: METASPACE_SIZE_MB
          value: "192"
        - name: COMPRESSED_CLASS_SPACE_SIZE_MB
          value: "64"
        - name: RESERVED_CODE_CACHE_SIZE_MB
          value: "128"
        - name: DIRECT_MEMORY_SIZE_MB
          value: "256"
        - name: JAVA_TOOL_OPTIONS
          value: >-
            -Xms$(HEAP_SIZE_MB)M
            -Xmx$(HEAP_SIZE_MB)M
            -Xss1M
            -XX:MaxMetaspaceSize=$(METASPACE_SIZE_MB)M
            -XX:CompressedClassSpaceSize=$(COMPRESSED_CLASS_SPACE_SIZE_MB)M
            -XX:ReservedCodeCacheSize=$(RESERVED_CODE_CACHE_SIZE_MB)M
            -XX:MaxDirectMemorySize=$(DIRECT_MEMORY_SIZE_MB)M
            -XX:+ExitOnOutOfMemoryError
Зачем -XX:+ExitOnOutOfMemoryError: если JVM получила критический OOM, процесс завершается, а Kubernetes перезапускает контейнер. Это часто лучше, чем оставить приложение в повреждённом состоянии. Но причина OOM всё равно должна расследоваться.

Runbook: проверка JVM memory-конфигурации при OOMKilled

1. Зафиксировать container memory limit
Понять, сколько памяти Kubernetes разрешает контейнеру.
kubectl describe pod -n <namespace> <pod> | egrep -A5 -i "limits|requests"
2. Проверить фактические JVM flags
Не доверяйте только deployment yaml: важно увидеть, какие флаги реально применились в процессе.
kubectl exec -n <namespace> <pod> -- sh -c 'jcmd 1 VM.flags'
3. Сравнить Xmx с memory limit
Если Xmx занимает почти весь limit, это сильный кандидат на причину OOMKilled.
4. Посчитать thread stacks
Оцените jvm_threads_live_threads × Xss. При сотнях потоков это значимый расход памяти.
5. Сравнить heap и container memory
Если heap не полный, а container memory близко к limit — ищите non-heap/direct/native/thread stacks.
6. Передать владельцам сервиса расчёт
В эскалации укажите memory limit, Xmx, metaspace, direct memory, Xss, thread count, RSS/container memory и время OOM.
Чего не делать: не увеличивайте -Xmx и memory limit вслепую как постоянное решение. Это может только отложить падение, увеличить длительность GC-пауз и скрыть настоящую утечку.

4. Garbage Collector

Зачем нужен Garbage Collector

Garbage Collector освобождает память от объектов, которые больше недостижимы из живых ссылок. Для поддержки важна практическая цепочка: приложение создаёт объекты → heap заполняется → GC освобождает память → во время пауз может расти latency → при нехватке памяти возможны Full GC, OOM и рестарты pod.

Запросы создают Java-объекты ↓ Объекты попадают в Young Generation ↓ Young Generation заполняется ↓ Minor GC очищает короткоживущие объекты ↓ Выжившие объекты постепенно стареют ↓ Долгоживущие объекты переходят в Old Generation ↓ Major / Full GC работает со старой областью ↓ Если живых объектов слишком много — паузы растут, возможен OOMKilled

Работа GC с поколениями

Классическая модель heap делит память на области для короткоживущих и долгоживущих объектов. Это сделано потому, что большинство объектов в типичном Java-приложении живут недолго: DTO, временные коллекции, строки, объекты парсинга JSON, промежуточные результаты обработки запроса.

ОбластьДля чего нужнаЧто важно поддержке
EdenСюда в первую очередь попадают новые объекты.Быстрое заполнение Eden означает высокий allocation rate.
Survivor S0 / S1Две области для объектов, которые пережили Minor GC.Объекты копируются между Survivor-областями и получают возраст.
Old GenerationХранит долгоживущие объекты.Рост Old Gen после GC — важный признак memory pressure или утечки.
Главная идея поколений: часто и быстро очищать молодые объекты, а более дорогую очистку старой области выполнять реже.

Minor GC: очистка Young Generation

Minor GC запускается, когда заполняется Young Generation, чаще всего Eden. Young Generation обычно состоит из одной области Eden и двух Survivor-областей: S0 и S1.

  1. Новые объекты сначала размещаются в Eden.
  2. Когда Eden заполняется, JVM инициирует Minor GC.
  3. GC ищет живые объекты в Eden и в активной Survivor-области.
  4. Живые объекты копируются в другую Survivor-область.
  5. Eden и предыдущая активная Survivor-область очищаются целиком.
  6. Объекты, пережившие несколько Minor GC, получают больший возраст.
  7. После достижения порога возраста объект переносится в Old Generation. Это называется старением или promotion.
До Minor GC: Eden: много новых объектов S0: объекты, пережившие прошлый GC S1: пусто После Minor GC: Eden: очищен S0: очищен S1: живые объекты из Eden и S0 Old Gen: часть достаточно старых объектов
Почему Minor GC обычно быстрый: он работает с небольшой молодой областью и копирует только живые объекты. Большинство временных объектов просто исчезают при очистке Eden.
Когда Minor GC становится проблемой: если приложение создаёт слишком много объектов, Minor GC начинает выполняться очень часто. Даже короткие паузы при высокой частоте могут заметно влиять на latency и CPU.

Старение объектов и promotion в Old Generation

Если объект переживает несколько Minor GC, JVM считает его долгоживущим. Такой объект постепенно «стареет» и затем перемещается в Old Generation. Это нормальный процесс, но для поддержки важно смотреть, насколько быстро растёт Old Generation.

ПаттернЧто означаетДействие поддержки
Old Gen растёт во время нагрузки, но после GC возвращается к baselineПохоже на нормальный рабочий набор объектов.Сравнить с RPS и latency.

Old Gen близко к максимумуРиск Full GC, OOM и рестарта.Проверить память, логи, GC, возможность собрать heap dump.

Major GC и Full GC: очистка старой области

Old Generation предназначена для долгоживущих объектов и обычно больше Young Generation. Когда старая область заполняется или JVM испытывает сильное давление по памяти, запускается более тяжёлая сборка мусора.

Major GC обычно связывают с очисткой Old Generation. Full GC часто означает более широкую остановку и обработку разных областей heap и JVM-памяти. В реальных логах и метриках терминология зависит от используемого GC, версии Java и формата логирования.

  1. GC определяет живые объекты в Old Generation.
  2. Недоступные объекты освобождаются.
  3. При необходимости живые объекты перемещаются, чтобы уменьшить фрагментацию памяти.
  4. Такое перемещение называется compaction, или уплотнение.
  5. Во время тяжёлых фаз приложение может переживать Stop-The-World паузы.
Stop-The-World: это пауза, во время которой потоки приложения приостанавливаются. Для пользователя это может выглядеть как резкий рост latency, timeout, срыв readiness/liveness probe или кратковременное зависание сервиса.

Что такое фрагментация памяти

Фрагментация означает, что свободная память есть, но она разбита на небольшие куски. Для размещения крупного объекта может не хватить непрерывного участка. Поэтому при Major/Full GC JVM может перемещать живые объекты и уплотнять память.

Runbook поддержки при подозрении на проблему GC

1. Сравнить GC pause и latency
Откройте p95/p99 latency и GC pause на одном временном окне. Важно понять, совпадают ли пики.
2. Проверить heap до и после GC
Если baseline heap после GC растёт, это похоже на рост live data или утечку.
3. Проверить allocation rate
Если heap очищается, но GC очень частый, причина может быть в большом количестве временных объектов.
4. Проверить CPU throttling
Ограничение CPU в Kubernetes может растягивать GC-паузы и ухудшать latency.
5. Собрать артефакты
Для CPU/allocation pressure — JFR. Для устойчивого роста Old Gen — heap dump. Для зависания во время пауз — thread dump рядом по времени.

5. HikariCP

Что такое HikariCP

HikariCP — это JDBC connection pool. Он держит набор заранее открытых соединений к PostgreSQL, чтобы приложение не создавало новое TCP/JDBC-соединение на каждый пользовательский запрос.

Когда поток приложения хочет выполнить SQL, он берёт connection из пула. После выполнения SQL connection должен быть возвращён обратно в пул. Если свободных соединений нет, поток ждёт. Если он не дождался за отведённое время, приложение получает timeout.

HTTP request thread ↓ берёт connection Hikari pool ├─ active connections: заняты запросами ├─ idle connections: свободны ├─ pending threads: ждут connection └─ max pool size: верхний лимит ↓ PostgreSQL sessions / backend processes
Главная идея: HikariCP защищает приложение от дорогого создания соединений, но сам пул может стать узким местом, если соединений мало, SQL медленные или PostgreSQL перегружен.

В Kubernetes у deployment 5 replicas, а maximumPoolSize=30. Сколько соединений этот deployment потенциально может открыть к PostgreSQL?

5.1 PostgreSQL и пул соединений

Каждый active connection в Hikari соответствует сессии на стороне PostgreSQL. Если у каждого pod большой pool, суммарное число соединений может перегрузить БД.

Формула: replicas × maximumPoolSize должно помещаться в допустимое число соединений PostgreSQL с запасом.
-- Активность подключений
select state, count(*)
from pg_stat_activity
group by state
order by count(*) desc;

-- Долгие активные запросы
select pid, usename, application_name, state,
       now() - query_start as duration,
       wait_event_type, wait_event,
       left(query, 500) as query
from pg_stat_activity
where state <> 'idle'
order by duration desc
limit 20;

-- Idle in transaction
select pid, usename, application_name,
       now() - xact_start as xact_duration,
       left(query, 500) as query
from pg_stat_activity
where state = 'idle in transaction'
order by xact_duration desc
limit 20;

6. Runbooks инцидентов

Сервис медленно отвечает

  1. Проверить масштаб: один pod, все replicas, один endpoint или вся система.
  2. Проверить RPS, p95/p99 latency, 5xx, CPU, memory, threads, Hikari.
  3. Если active threads=max или много waiting — снять thread dump.
  4. Если Hikari pending растёт — проверить PostgreSQL.
  5. Если GC pause совпадает с latency — собрать JFR и GC-графики.

Pod OOMKilled

  1. Зафиксировать pod, namespace, restart count, время OOM.
  2. Снять previous logs.
  3. Проверить container memory vs limit, heap, non-heap, threads.
  4. Если другая replica показывает такой же рост heap — снять heap dump.
  5. Проверить релиз, нагрузку, batch, изменение payload.

Hikari пул соединений исчерпан

  1. Проверить active=max, idle=0, pending>0, timeout rate.
  2. Сравнить с HTTP latency и 5xx.
  3. Проверить usage/acquire time.
  4. Снять thread dump.
  5. Проверить PostgreSQL: slow queries, locks, idle in transaction.
  6. Не увеличивать maximumPoolSize вслепую.

Призыв к действию

Что должен сделать прикладной администратор после курса

Курс должен закончиться не только прочтением, а практической проверкой готовности сервиса к production-инциденту. Ниже — минимальный набор действий, который стоит отработать на тестовом контуре или согласованном стенде.

1

🧳 Снять heap dump

Проверьте, что умеете снять heap dump, проверить свободное место, скопировать файл из pod и удалить его после копирования.

2

📄 Снять thread dump

Отработайте снятие трёх thread dump с интервалом 10–15 секунд, чтобы видеть не один кадр, а динамику потоков.

3

🧠 Проверить параметры Java heap

Убедитесь, что параметры -Xms, -Xmx, -Xss, Metaspace, Code Cache и Direct Memory вынесены в конфигурацию.

4

🏊 Проверить параметры HikariCP

Проверьте, что maximumPoolSize, minimumIdle, connectionTimeout, maxLifetime, keepaliveTime и poolName задаются явно.

5

🖥️ Проверить дашборды

Убедитесь, что настроены Grafana-панели для мониторинга threads, HikariCP и процента занятого heap.

Итог

🚀 Подготовить сервис к аварии

Метрики, параметры запуска, команды диагностики и runbook должны быть готовы до инцидента, а не во время него.

Финальная цель: прикладной администратор должен быстро собрать факты: что случилось, где случилось, когда началось, какие артефакты собраны и что передано владельцам сервиса.
