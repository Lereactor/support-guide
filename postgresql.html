1. Общее устройство PostgreSQL и HA-кластера Patroni + etcd + HAProxy

PostgreSQL сам по себе

PostgreSQL — это сервер базы данных, который хранит данные в data directory. Один экземпляр PostgreSQL состоит из процессов, общей памяти, файлов данных и WAL-журнала.

  • Postmaster / postgres process — главный процесс, принимает подключения и запускает backend-процессы.
  • Backend processes — процессы, которые обслуживают клиентские соединения. Обычно одно подключение = один backend-процесс.
  • Shared Buffers — область общей памяти, где PostgreSQL кэширует страницы таблиц и индексов.
  • WAL — Write-Ahead Log — журнал предзаписи. Перед изменением data files изменение сначала фиксируется в WAL.
  • Data files — физические файлы таблиц, индексов, TOAST-данных и системных каталогов.
  • Autovacuum — фоновый механизм очистки старых версий строк, необходимых из-за MVCC.
ps -ef | grep postgres

Важно для поддержки: если приложение жалуется на медленную БД, проблема может быть не только в SQL, но и в количестве подключений, нехватке памяти, WAL, диске или autovacuum.

Базовая репликация PostgreSQL

В production PostgreSQL часто работает не один сервер, а кластер с primary и replica.

Primary PostgreSQL
        |
        | WAL streaming
        v
Replica PostgreSQL
        |
        v
Replica PostgreSQL

Primary принимает запись: INSERT, UPDATE, DELETE, DDL.

Replica получает WAL с primary и применяет его у себя.

  • Асинхронная репликация — primary подтверждает транзакцию сразу, не дожидаясь replica. Быстрее, но при аварии можно потерять последние транзакции.
  • Синхронная репликация — primary ждёт подтверждения от replica. Надёжнее, но медленнее.

Зачем нужен Patroni

PostgreSQL сам по себе не является полноценным менеджером автоматического failover. Он умеет репликацию, но не управляет всем жизненным циклом HA-кластера.

Patroni — менеджер высокой доступности PostgreSQL.

Он выполняет задачи:

  • следит за состоянием PostgreSQL;
  • выбирает primary;
  • переводит replica в primary при аварии;
  • настраивает репликацию;
  • защищает от split-brain;
  • хранит состояние кластера в DCS.

DCS — Distributed Configuration Store. Обычно используется etcd, Consul или ZooKeeper.

Роль etcd

etcd — распределённое key-value хранилище. В PostgreSQL HA-кластере etcd не хранит данные базы. Он хранит служебное состояние кластера.

  • кто сейчас primary;
  • какие ноды живы;
  • leader lock текущего primary;
  • параметры Patroni;
  • TTL-состояния участников.
/service/postgres-cluster/leader = pg-node-1
/service/postgres-cluster/members/pg-node-1 = alive
/service/postgres-cluster/members/pg-node-2 = replica

Patroni-ноды постоянно обновляют записи в etcd. Primary держит leader lock. Если primary падает и перестаёт обновлять lock, другая replica может стать новым primary.

Типовая схема HA-кластера

                 Application
                      |
                      v
                  HAProxy / VIP
                      |
        +-------------+-------------+
        |                           |
        v                           v
   PostgreSQL node 1           PostgreSQL node 2
   Patroni + PostgreSQL        Patroni + PostgreSQL
   Primary or Replica          Primary or Replica
        |                           |
        +-------------+-------------+
                      |
                      v
                    etcd cluster
              etcd-1 / etcd-2 / etcd-3

Обычно production-схема включает:

  • 3 etcd-ноды;
  • 3 PostgreSQL-ноды с Patroni;
  • 1–2 HAProxy-ноды;
  • опционально Keepalived/VIP перед HAProxy.

Как работает failover

Пример исходного состояния:

pg-1 = primary
pg-2 = replica
pg-3 = replica

Если pg-1 падает:

  1. Patroni на pg-1 перестаёт обновлять lock в etcd.
  2. etcd удаляет lock после TTL.
  3. Patroni на репликах видит, что leader отсутствует.
  4. Самая подходящая replica становится новым primary.
  5. Например, pg-2 promoted to primary.
  6. HAProxy через health-check видит, что primary теперь pg-2.
  7. Новые подключения идут на pg-2.

После failover:

pg-2 = primary
pg-3 = replica
pg-1 = бывший primary, требует rejoin/reinit

Важно для поддержки: после failover старый primary нельзя просто возвращать как primary. Его нужно корректно присоединить обратно через pg_rewind или reinit.

Роль HAProxy

HAProxy скрывает от приложения, какая PostgreSQL-нода сейчас primary.

postgres://app:pass@haproxy:5432/db

HAProxy проверяет Patroni REST API на каждой ноде:

GET http://pg-1:8008/primary
GET http://pg-2:8008/primary
GET http://pg-3:8008/primary

Только текущий primary отдаёт успешный ответ на primary/master endpoint. HAProxy отправляет write-трафик туда.

Часто используют два порта:

5000 -> primary, для записи
5001 -> replicas, для чтения
Application write traffic -> HAProxy:5000 -> current primary
Application read traffic  -> HAProxy:5001 -> replicas

Patroni REST API и patronictl

Patroni поднимает HTTP API, обычно на порту 8008.

  • /primary или /master — проверка primary;
  • /replica — проверка replica;
  • /health — состояние сервиса;
  • /patroni — подробная информация Patroni.
patronictl list

Split-brain

Split-brain — опасная ситуация, когда две ноды одновременно считают себя primary.

pg-1 принимает записи
pg-2 тоже принимает записи
данные расходятся

Patroni + etcd нужны, чтобы этого не произошло. Только нода, владеющая leader lock в etcd, имеет право быть primary.

Что происходит со старым primary после аварии

Когда бывший primary возвращается после сбоя, Patroni не должен сразу пускать его обратно как primary.

Обычно выполняется:

  • проверка timeline;
  • сравнение WAL-позиции;
  • попытка pg_rewind;
  • если rewind невозможен — reinit.

pg_rewind позволяет быстро превратить бывший primary в replica нового primary, если нужный WAL ещё доступен.

Компоненты и их роли

  • PostgreSQL — хранит данные и выполняет SQL.
  • Patroni — управляет PostgreSQL-нодами, failover, promote, demote, reinit.
  • etcd — хранит состояние кластера и leader lock.
  • HAProxy — направляет клиентские подключения на правильную PostgreSQL-ноду.
  • Keepalived / VIP — даёт единый виртуальный IP для HAProxy.
  • pgBackRest / Barman — backup и restore.
  • Prometheus / Grafana — мониторинг.
  • WAL archive — долговременное хранение WAL для восстановления.

Упрощённый поток записи

  1. Приложение подключается к HAProxy.
  2. HAProxy отправляет соединение на текущий primary.
  3. PostgreSQL пишет изменения в WAL.
  4. Primary применяет изменения к data files.
  5. WAL передаётся replica-нодам.
  6. Replica применяют WAL.
  7. Patroni следит за состоянием.
  8. etcd хранит информацию, кто leader.

App -> HAProxy -> PostgreSQL Primary

Идея HA-кластера: если primary падает, replica автоматически становится новым primary, а приложение продолжает работать через HAProxy.

2. MVCC — многоверсионность PostgreSQL

Что такое MVCC

MVCC (Multiversion Concurrency Control) — многоверсионное управление конкурентным доступом. PostgreSQL поддерживает целостность данных так, что каждый SQL-оператор видит не «текущую физическую таблицу», а снимок данных на определённый момент времени.

Это защищает запросы от несогласованности, если параллельные транзакции меняют те же строки. Главное преимущество MVCC: чтение не блокирует запись, а запись не блокирует чтение. Благодаря этому PostgreSQL хорошо работает в многопользовательской среде.

Даже для строгой изоляции PostgreSQL использует подход SSI — Serializable Snapshot Isolation.

Версии строк

В PostgreSQL строка может существовать физически в нескольких версиях. При UPDATE старая версия не переписывается на месте: создаётся новая версия, а старая помечается как устаревшая.

  • INSERT создаёт новую версию строки.
  • DELETE помечает текущую версию как удалённую.
  • UPDATE фактически работает как DELETE старой версии + INSERT новой версии.

Именно поэтому после большого количества UPDATE/DELETE появляются «мёртвые» версии строк, которые затем должен убрать VACUUM.

xmin, xmax и ctid

У каждой версии строки есть служебные поля в заголовке:

  • xmin — номер транзакции, которая создала эту версию строки;
  • xmax — номер транзакции, которая удалила или заменила эту версию;
  • ctid — физическая ссылка на версию строки в виде (страница, указатель);
  • infomask — набор битов статуса, например была ли транзакция зафиксирована или отменена.
SELECT xmin, xmax, ctid, * FROM accounts;

Если строка актуальна, обычно xmax = 0. Если строка обновлялась, старая версия получает xmax, а новая версия получает новый xmin.

Важно: заголовок версии строки занимает минимум около 23 байт, поэтому для очень «узких» таблиц служебные накладные расходы могут быть заметными.

Как работает INSERT

При вставке строки PostgreSQL создаёт новую версию строки и записывает в xmin номер текущей транзакции. Пока транзакция не завершена, другие транзакции не считают эту версию видимой.

BEGIN;
INSERT INTO t(s) VALUES ('FOO');
SELECT txid_current();
COMMIT;

После COMMIT статус транзакции записывается в служебные структуры PostgreSQL. Позже при чтении страницы PostgreSQL может выставить так называемые hint bits, чтобы последующие проверки видимости были быстрее.

Как работает DELETE

DELETE не стирает строку физически сразу. Он записывает номер удаляющей транзакции в xmax текущей версии строки.

BEGIN;
DELETE FROM t WHERE id = 1;
ROLLBACK;

Если транзакция отменена, версия строки остаётся видимой. Если транзакция зафиксирована, версия становится мёртвой для новых снимков и позже может быть очищена VACUUM.

xmax активной транзакции также работает как признак блокировки строки: другая транзакция, желающая изменить эту же строку, будет ждать завершения первой.

Как работает UPDATE

UPDATE создаёт новую версию строки и связывает старую с новой через ctid.

BEGIN;
UPDATE t SET s = 'BAR' WHERE id = 1;
COMMIT;

Физически в странице могут оказаться две версии:

ctid   xmin       xmax       t_ctid
(0,1)  3664 (c)   3666       (0,2)
(0,2)  3666       0          (0,2)

Первая версия стала старой, вторая — новой актуальной версией. Для разных транзакций, в зависимости от их snapshot, видимой может быть разная версия.

Индексы и MVCC

В индексах PostgreSQL нет собственных версий строк с xmin/xmax. Индексная запись обычно содержит ключ и ссылку ctid на табличную версию строки.

После UPDATE индекс может содержать ссылки и на старую, и на новую версии строки. Чтобы понять, какая версия видима текущей транзакции, PostgreSQL должен проверить табличную строку и правила видимости.

В некоторых случаях visibility map позволяет оптимизировать чтение, например для Index Only Scan.

Снимок данных (Snapshot)

Snapshot — это не физическая копия таблиц. Это набор чисел, по которым PostgreSQL определяет, какие версии строк видны транзакции.

Упрощённо версия строки видима, если:

  • транзакция xmin, создавшая версию, уже видима в снимке;
  • транзакция xmax, удалившая или заменившая версию, ещё не видима в снимке.

В snapshot важны:

  • snapshot.xmin — самая ранняя активная транзакция;
  • snapshot.xmax — номер следующей ещё не существующей транзакции;
  • snapshot.xip — список активных транзакций на момент создания снимка.
SELECT txid_current_snapshot();

Пример вида snapshot:

3695:3697:3695

Это означает: xmin = 3695, xmax = 3697, активная транзакция в списке — 3695.

Когда создаётся snapshot

  • Read Committed — новый snapshot создаётся в начале каждого SQL-оператора.
  • Repeatable Read — snapshot создаётся один раз в начале первого значимого оператора транзакции.
  • Serializable — также использует стабильный snapshot, но дополнительно отслеживает опасные зависимости.

Поэтому в Read Committed два SELECT внутри одной транзакции могут видеть разные данные, а в Repeatable Read — один и тот же снимок.

Виртуальные и настоящие транзакции

Если транзакция только читает данные, PostgreSQL сначала может назначить ей только виртуальный transaction id. Настоящий XID выдаётся, когда транзакция начинает менять данные.

BEGIN;
SELECT txid_current_if_assigned(); -- может вернуть NULL
UPDATE accounts SET amount = amount - 1;
SELECT txid_current_if_assigned(); -- теперь появится XID
COMMIT;

Это экономит реальные номера транзакций и снижает накладные расходы.

Savepoint и вложенные транзакции

Точки сохранения реализуются через вложенные транзакции (subtransactions). У них есть собственные номера и собственный статус, но итоговая судьба зависит от основной транзакции.

BEGIN;
INSERT INTO t VALUES (1);
SAVEPOINT sp;
INSERT INTO t VALUES (2);
ROLLBACK TO sp;
INSERT INTO t VALUES (3);
COMMIT;

Физически версия строки, добавленная отменённой вложенной транзакцией, может остаться в странице, но будет невидима и позже очищена VACUUM.

Важно: автономных транзакций в обычном PostgreSQL нет. Savepoint — это не независимая транзакция.

Ошибки и атомарность оператора

Если внутри транзакции произошла ошибка, транзакция переходит в состояние aborted. Дальнейшие команды запрещены до ROLLBACK.

BEGIN;
UPDATE t SET s = repeat('X', 1/(id-4));
-- ERROR: division by zero
SELECT * FROM t;
-- ERROR: current transaction is aborted
ROLLBACK;

Это нужно, чтобы не нарушить атомарность SQL-оператора. Некоторые изменения могли физически попасть в страницы, но логически они должны считаться отменёнными.

В psql режим ON_ERROR_ROLLBACK имитирует откат ошибочного оператора через неявные savepoint, но это даёт дополнительные накладные расходы.

Горизонт событий и почему долгие транзакции вредны

snapshot.xmin определяет «горизонт событий». За этим горизонтом старые версии строк уже точно не нужны ни одной активной транзакции и могут быть очищены.

Если транзакция долго остаётся открытой, она удерживает горизонт. Из-за этого VACUUM не может удалить старые версии строк, даже если эта транзакция не обращается к тем же таблицам.

SELECT backend_xmin
FROM pg_stat_activity
WHERE pid = pg_backend_pid();

Типовой production-инцидент: сессия idle in transaction висит несколько часов, autovacuum не может очистить dead tuples, таблицы и индексы раздуваются, запросы начинают замедляться.

Полезные настройки:

  • idle_in_transaction_session_timeout — завершает слишком долгие idle in transaction;
  • old_snapshot_threshold — ограничивал жизнь старых снимков в старых версиях PostgreSQL, но в современных версиях важно проверять актуальность поддержки параметра.

Экспорт snapshot

Иногда нескольким транзакциям нужно видеть одну и ту же картину данных. Например, параллельный pg_dump должен делать согласованную резервную копию.

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT pg_export_snapshot();

Другая транзакция может импортировать snapshot до первого запроса:

BEGIN ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION SNAPSHOT '00000004-00000E7B-1';

Время жизни экспортированного snapshot равно времени жизни экспортирующей транзакции.

Что должна понимать поддержка

  • MVCC даёт высокую конкурентность: читатели и писатели обычно не мешают друг другу.
  • UPDATE создаёт новые версии строк, поэтому частые UPDATE вызывают bloat.
  • VACUUM нужен для удаления старых версий.
  • Долгие транзакции и idle in transaction удерживают горизонт очистки.
  • Индексы могут ссылаться на старые версии строк до очистки.
  • Проблемы MVCC часто проявляются как рост таблиц, рост индексов, медленные запросы и невозможность autovacuum очистить dead tuples.

3. Изоляция транзакций в PostgreSQL

Что такое изоляция транзакций

Изоляция транзакций определяет, какие изменения, выполняемые параллельными транзакциями, видны текущей транзакции. Чем выше уровень изоляции, тем меньше аномалий возможно, но тем выше вероятность конфликтов, повторов транзакций и накладных расходов.

Стандарт SQL определяет четыре уровня изоляции:

  • Read Uncommitted
  • Read Committed
  • Repeatable Read
  • Serializable

В PostgreSQL фактически реализованы три разных поведения: Read Uncommitted работает как Read Committed, потому что архитектура MVCC не допускает грязного чтения.

Аномалии параллельных транзакций

  • Грязное чтение — транзакция читает данные, записанные другой незавершённой транзакцией.
  • Неповторяемое чтение — транзакция повторно читает те же данные и видит, что они изменились после фиксации другой транзакции.
  • Фантомное чтение — повторный запрос по условию возвращает другой набор строк из-за параллельной зафиксированной транзакции.
  • Аномалия сериализации — результат параллельного выполнения транзакций нельзя объяснить никаким последовательным порядком их выполнения.

Таблица уровней изоляции

Уровень                Грязное чтение   Неповторяемое   Фантомы        Аномалия сериализации
Read Uncommitted       Нет в PG         Возможно        Возможно       Возможно
Read Committed         Невозможно       Возможно        Возможно       Возможно
Repeatable Read        Невозможно       Невозможно      Нет в PG       Возможно
Serializable           Невозможно       Невозможно      Невозможно     Невозможно

Важно: PostgreSQL в некоторых местах строже стандарта. Например, Repeatable Read в PostgreSQL не допускает фантомного чтения, хотя стандарт SQL допускает его для этого уровня.

Как выбрать уровень изоляции

BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN ISOLATION LEVEL REPEATABLE READ;

BEGIN ISOLATION LEVEL SERIALIZABLE;

Уровень изоляции задаётся командой SET TRANSACTION или прямо при начале транзакции.

Особенность последовательностей: изменения sequence / serial видны другим транзакциям сразу и не откатываются при ROLLBACK. Это нормальное поведение PostgreSQL.

Read Committed — уровень по умолчанию

Read Committed — стандартный уровень изоляции в PostgreSQL.

На этом уровне обычный SELECT видит только данные, зафиксированные до начала конкретного SQL-оператора. Он не видит незавершённых изменений других транзакций.

Главная особенность: два SELECT внутри одной транзакции могут увидеть разные данные, если между ними другая транзакция успела зафиксировать изменения.

BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- другая транзакция обновила balance и сделала COMMIT
SELECT balance FROM accounts WHERE id = 1;
COMMIT;

Во втором SELECT значение может быть уже другим.

UPDATE / DELETE / SELECT FOR UPDATE

Команды изменения ищут строки по снимку на начало команды. Но если найденная строка уже изменяется другой транзакцией, PostgreSQL ждёт её завершения. После этого условие WHERE проверяется заново на новой версии строки.

Это важно: команда может работать с изменённой версией строки, хотя изначально видела другую.

ON CONFLICT и MERGE

В Read Committed команда INSERT ... ON CONFLICT DO UPDATE гарантирует, что строка будет либо вставлена, либо обновлена, даже если конфликт вызван параллельной транзакцией, результат которой ещё не был видим обычному снимку INSERT.

MERGE ведёт себя сложнее: условия действий могут переоцениваться для обновлённой версии строки. Поэтому при сопровождении важно внимательно анализировать MERGE в конкурентной нагрузке.

Когда подходит Read Committed

  • обычные OLTP-операции;
  • простые UPDATE по ключу;
  • типовые операции приложения;
  • сценарии, где не требуется стабильный снимок всей транзакции.

Когда может быть опасен

  • сложные условия поиска;
  • многошаговая бизнес-логика;
  • расчёты, где все SELECT должны видеть один и тот же снимок;
  • конкурентные DELETE/UPDATE по изменяемым условиям.

Пример особенности Read Committed

Представим таблицу website с двумя строками, где hits равны 9 и 10.

-- Транзакция 1
BEGIN;
UPDATE website SET hits = hits + 1;
COMMIT;

-- Параллельно транзакция 2
DELETE FROM website WHERE hits = 10;

DELETE может не удалить ни одной строки: строка с 9 ещё не подходит, а строка с 10 может быть изменена другой транзакцией и после ожидания уже иметь значение 11. Поэтому условие WHERE переоценивается и строка больше не подходит.

Вывод для поддержки: Read Committed быстрый и удобный, но одна команда не всегда видит «идеально согласованную» картину всей базы.

Repeatable Read

Repeatable Read даёт транзакции стабильный снимок данных. Все SELECT внутри транзакции видят данные, зафиксированные до начала первого значимого оператора транзакции.

Изменения других транзакций, зафиксированные после начала текущей транзакции, не видны.

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM orders WHERE status = 'new';
-- другая транзакция добавила новый order и COMMIT
SELECT * FROM orders WHERE status = 'new';
COMMIT;

Оба SELECT увидят один и тот же снимок.

Конфликты изменения

Если транзакция Repeatable Read пытается изменить строку, которую после начала её снимка уже изменила и зафиксировала другая транзакция, текущая транзакция завершится ошибкой:

ERROR: could not serialize access due to concurrent update

После такой ошибки приложение должно повторить всю транзакцию с начала.

Особенности

  • реализуется через Snapshot Isolation;
  • SELECT получает стабильную картину данных;
  • read-only транзакции не получают конфликтов сериализации;
  • изменяющие транзакции должны быть готовы к retry;
  • фантомное чтение в PostgreSQL на этом уровне не возникает.

Когда использовать

  • отчёты, где нужен стабильный снимок;
  • длинные аналитические чтения;
  • операции, где повторные SELECT должны видеть одни и те же данные;
  • сложные проверки перед изменениями, но с готовностью к повтору транзакции.

Serializable

Serializable — самый строгий уровень изоляции. Он гарантирует, что результат успешно зафиксированных параллельных транзакций будет таким, как если бы они выполнялись последовательно в некотором порядке.

По поведению он похож на Repeatable Read, но дополнительно отслеживает зависимости чтения/записи, которые могли бы привести к аномалиям сериализации.

Пример аномалии

-- Транзакция A
SELECT SUM(value) FROM mytab WHERE class = 1;
INSERT INTO mytab(class, value) VALUES (2, 30);

-- Транзакция B
SELECT SUM(value) FROM mytab WHERE class = 2;
INSERT INTO mytab(class, value) VALUES (1, 300);

В Repeatable Read обе транзакции могли бы зафиксироваться, хотя общий результат не соответствует никакому последовательному порядку. В Serializable одна из них будет отменена.

ERROR: could not serialize access due to read/write dependencies among transactions

Типичный SQLSTATE для такой ошибки — 40001. Приложение должно повторить транзакцию.

Predicate locks / SIReadLock

Для Serializable PostgreSQL использует предикатные блокировки. Они не блокируют данные физически и не вызывают deadlock, но помогают обнаружить опасные зависимости между транзакциями.

SELECT * FROM pg_locks WHERE mode = 'SIReadLock';

Какие SIReadLock появятся, зависит от плана запроса. Например, последовательное сканирование может привести к предикатной блокировке уровня таблицы, что увеличивает вероятность serialization failure.

DEFERRABLE READ ONLY

Транзакция SERIALIZABLE READ ONLY DEFERRABLE может подождать безопасный снимок и затем читать данные без риска serialization anomaly.

BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;

Рекомендации

  • объявлять транзакции READ ONLY, если они только читают;
  • не держать транзакции открытыми дольше необходимого;
  • не оставлять сессии idle in transaction;
  • использовать пул соединений для контроля числа активных транзакций;
  • реализовать retry для SQLSTATE 40001;
  • убирать лишние SELECT FOR UPDATE/SHARE, если Serializable уже даёт нужную защиту;
  • следить за max_pred_locks_per_transaction, max_pred_locks_per_relation, max_pred_locks_per_page;
  • избегать неоправданных Seq Scan в Serializable, если они вызывают много SIReadLock на уровне таблицы.

Сравнение уровней для поддержки

  • Read Committed — быстрый и простой, но каждый оператор видит свой снимок.
  • Repeatable Read — стабильный снимок на всю транзакцию, возможны ошибки при конкурентных изменениях.
  • Serializable — максимальная согласованность, но обязательно нужен retry при serialization failure.

Практическое правило: если приложение жалуется на ошибки сериализации — это не обязательно авария PostgreSQL. Часто это нормальное поведение строгого уровня изоляции, и приложение должно корректно повторять транзакцию.

4. Блокировки (Locks) — расширенный разбор

PostgreSQL использует систему блокировок для управления конкурентным доступом к данным. Несмотря на MVCC, блокировки необходимы для операций изменения структуры данных и защиты от конфликтов при записи.

Общий принцип

Блокировки бывают:

  • Явные — задаются приложением через LOCK
  • Неявные — автоматически ставятся SQL-командами

Большинство команд (SELECT, UPDATE, ALTER, TRUNCATE) автоматически получают блокировки нужного уровня.

Уровни блокировок таблиц

Все блокировки работают на уровне таблицы (даже если содержат "row" в названии).

  • ACCESS SHARE — обычный SELECT
  • ROW EXCLUSIVE — INSERT / UPDATE / DELETE
  • SHARE UPDATE EXCLUSIVE — VACUUM, ANALYZE
  • SHARE — CREATE INDEX
  • EXCLUSIVE — REFRESH MATERIALIZED VIEW
  • ACCESS EXCLUSIVE — DROP, TRUNCATE, VACUUM FULL

Важно: ACCESS EXCLUSIVE блокирует ВСЕ операции, включая SELECT.

Как работает конфликт блокировок

Разные режимы блокировок конфликтуют друг с другом. Две транзакции не могут одновременно владеть несовместимыми блокировками одной таблицы.

Блокировки строк (Row-level locks)

Используются для точечных изменений строк:

  • FOR UPDATE — блокирует строку для изменения
  • FOR NO KEY UPDATE — слабее FOR UPDATE
  • FOR SHARE — блокировка для чтения с защитой
  • FOR KEY SHARE — минимальная блокировка ключей

Важно: блокировки строк не влияют на SELECT без FOR UPDATE.

pg_locks

Текущее состояние блокировок можно анализировать через системное представление:

SELECT * FROM pg_locks;

Deadlocks (взаимоблокировки)

Возникают, когда транзакции блокируют друг друга по кругу. PostgreSQL автоматически обнаруживает deadlock и завершает одну из транзакций.

Причина: разный порядок обновления ресурсов.

Рекомендательные блокировки (Advisory Locks)

Используются приложением вручную для управления логикой блокировок.

  • могут быть session-level или transaction-level
  • не привязаны к таблицам
  • удерживаются приложением

Опасность: использование с LIMIT / ORDER BY может привести к неожиданным блокировкам.

SELECT pg_advisory_lock(id) FROM foo WHERE id = 123;

Практические рекомендации поддержки

  • проверять pg_locks при зависаниях
  • искать блокирующие транзакции в pg_stat_activity
  • избегать долгих транзакций
  • следить за порядком обновления таблиц

5. VACUUM и autovacuum (расширенный разбор)

VACUUM — операция обслуживания PostgreSQL, предназначенная для очистки «мёртвых» кортежей (строк), оставшихся после UPDATE/DELETE, а также для возможного анализа статистики.

Синтаксис

VACUUM [ ( параметры [, ...] ) ] [ таблица ]
VACUUM [ FULL ] [ FREEZE ] [ VERBOSE ] [ ANALYZE ] [ таблица ]

Поддерживаемые параметры включают:

  • FULL — полная переразметка таблицы
  • FREEZE — агрессивная заморозка транзакций
  • VERBOSE — подробный вывод
  • ANALYZE — обновление статистики планировщика
  • INDEX_CLEANUP (AUTO/ON/OFF)
  • TRUNCATE — обрезка пустых страниц
  • PARALLEL — параллельная очистка
  • SKIP_LOCKED — пропуск заблокированных таблиц
  • PROCESS_MAIN / PROCESS_TOAST
  • BUFFER_USAGE_LIMIT — лимит буфера стратегии

Как работает VACUUM

PostgreSQL не удаляет строки физически сразу после UPDATE/DELETE. Вместо этого остаются «мёртвые версии строк». VACUUM освобождает это пространство и делает его доступным для повторного использования.

Важно: обычный VACUUM не возвращает место операционной системе, а только переиспользует его внутри таблицы.

VACUUM vs VACUUM FULL

  • VACUUM — безопасен, не блокирует таблицу, работает параллельно
  • VACUUM FULL — переписывает таблицу заново, освобождает место на диске, но блокирует ACCESS EXCLUSIVE

Почему VACUUM важен

  • предотвращает разрастание таблиц (bloat)
  • обновляет статистику для планировщика
  • предотвращает wraparound транзакций
  • улучшает производительность SELECT

Autovacuum — автоматическая очистка

Autovacuum — механизм PostgreSQL, который автоматически запускает VACUUM и ANALYZE в зависимости от активности изменений в таблицах.

Обычный VACUUM хорошо справляется со своей задачей, если никто надолго не удерживает горизонт транзакций. Главный вопрос — как часто его запускать:

  • если чистить таблицу слишком редко — она раздувается, растёт bloat, а следующая очистка может потребовать несколько проходов по индексам;
  • если чистить слишком часто — сервер будет тратить ресурсы на обслуживание вместо полезной работы;
  • очистка «по расписанию» не всегда подходит, потому что нагрузка меняется: если таблицу стали обновлять активнее, чистить её тоже нужно чаще.

Autovacuum решает эту задачу: он запускает очистку не просто по времени, а по статистике изменений в таблицах.

Процессы autovacuum

  • autovacuum launcher — постоянно присутствует в системе и планирует работу;
  • autovacuum worker — рабочий процесс, который подключается к базе и выполняет VACUUM/ANALYZE;
  • postmaster — запускает worker-процессы по запросу launcher.
autovacuum launcher
        |
        v
autovacuum worker -> database -> tables/materialized views/toast

Launcher составляет список баз данных, где есть активность. Активность определяется по статистике, поэтому критически важно:

autovacuum = on
track_counts = on

Никогда не выключайте autovacuum и track_counts без очень веской причины. Если track_counts выключен, автоочистка не сможет принимать решения по статистике.

Как часто запускаются worker-процессы

Раз в autovacuum_naptime launcher запускает worker для каждой активной базы данных. Если активных баз несколько, worker-процессы могут запускаться чаще, но общее число одновременно работающих worker ограничено:

autovacuum_naptime
autovacuum_max_workers

Если worker не успевает обработать всё за один интервал, launcher может отправить в ту же БД ещё один worker. Они будут работать параллельно, но разные worker обрабатывают разные таблицы. На уровне одной таблицы autovacuum не параллелится: если один worker уже занимается таблицей, другой её пропустит.

Какие объекты выбирает worker

После подключения к базе worker строит список объектов:

  • таблицы, материализованные представления и TOAST-таблицы, требующие VACUUM;
  • таблицы и материализованные представления, требующие ANALYZE;
  • TOAST-таблицы не анализируются, потому что доступ к ним обычно идёт через индекс.

Когда таблице нужен VACUUM

Очистка нужна, если число мёртвых версий строк превысило порог:

pg_stat_all_tables.n_dead_tup >=
  autovacuum_vacuum_threshold
  + autovacuum_vacuum_scale_factor * pg_class.reltuples

Параметры по умолчанию:

autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.2

Практический вывод: значение 0.2 означает 20% таблицы. Для больших активно изменяемых таблиц это часто слишком много, поэтому scale factor обычно уменьшают, например до 0.01–0.05.

Порог можно задавать глобально или на уровне конкретной таблицы:

ALTER TABLE orders SET (
  autovacuum_vacuum_threshold = 1000,
  autovacuum_vacuum_scale_factor = 0.02
);

Для TOAST-таблиц есть отдельные параметры хранения:

toast.autovacuum_vacuum_threshold
toast.autovacuum_vacuum_scale_factor

Отключение autovacuum на уровне таблицы возможно, но почти всегда опасно:

ALTER TABLE orders SET (autovacuum_enabled = off);

Представление для поиска таблиц, которым нужен VACUUM

Для обучения и диагностики можно создать вспомогательную функцию, которая учитывает переопределения параметров на уровне таблицы:

CREATE FUNCTION get_value(param text, reloptions text[], relkind "char")
RETURNS float
AS $$
  SELECT coalesce(
    (SELECT option_value
     FROM pg_options_to_table(reloptions)
     WHERE option_name = CASE
       WHEN relkind = 't' THEN 'toast.' ELSE ''
     END || param),
    current_setting(param)
  )::float;
$$ LANGUAGE sql;

Представление для оценки необходимости VACUUM:

CREATE VIEW need_vacuum AS
SELECT st.schemaname || '.' || st.relname AS tablename,
       st.n_dead_tup AS dead_tup,
       get_value('autovacuum_vacuum_threshold', c.reloptions, c.relkind) +
       get_value('autovacuum_vacuum_scale_factor', c.reloptions, c.relkind) * c.reltuples
       AS max_dead_tup,
       st.last_autovacuum
FROM pg_stat_all_tables st
JOIN pg_class c ON c.oid = st.relid
WHERE c.relkind IN ('r','m','t');
SELECT * FROM need_vacuum ORDER BY dead_tup DESC;

Когда таблице нужен ANALYZE

Автоанализ запускается по похожей формуле, но использует количество изменённых строк с момента прошлого анализа:

pg_stat_all_tables.n_mod_since_analyze >=
  autovacuum_analyze_threshold
  + autovacuum_analyze_scale_factor * pg_class.reltuples

Параметры по умолчанию:

autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.1

Их тоже можно задавать на уровне таблицы:

ALTER TABLE orders SET (
  autovacuum_analyze_threshold = 1000,
  autovacuum_analyze_scale_factor = 0.02
);

TOAST-таблицы не анализируются, поэтому отдельных toast-параметров для analyze нет.

Представление для поиска таблиц, которым нужен ANALYZE:

CREATE VIEW need_analyze AS
SELECT st.schemaname || '.' || st.relname AS tablename,
       st.n_mod_since_analyze AS mod_tup,
       get_value('autovacuum_analyze_threshold', c.reloptions, c.relkind) +
       get_value('autovacuum_analyze_scale_factor', c.reloptions, c.relkind) * c.reltuples
       AS max_mod_tup,
       st.last_autoanalyze
FROM pg_stat_all_tables st
JOIN pg_class c ON c.oid = st.relid
WHERE c.relkind IN ('r','m');
SELECT * FROM need_analyze ORDER BY mod_tup DESC;

Пример логики срабатывания

Если настроить пороги так:

ALTER SYSTEM SET autovacuum_naptime = '1s';
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = 0.03;
ALTER SYSTEM SET autovacuum_vacuum_threshold = 0;
ALTER SYSTEM SET autovacuum_analyze_scale_factor = 0.02;
ALTER SYSTEM SET autovacuum_analyze_threshold = 0;
SELECT pg_reload_conf();

Для таблицы на 1000 строк порог VACUUM будет примерно 30 мёртвых строк, а порог ANALYZE — примерно 20 изменённых строк.

CREATE TABLE autovac(
  id serial,
  s char(100)
) WITH (autovacuum_enabled = off);

INSERT INTO autovac SELECT g.id, 'A'
FROM generate_series(1,1000) g(id);

После INSERT в таблице ещё нет мёртвых строк, поэтому VACUUM не нужен. Но изменённых строк много, поэтому нужен ANALYZE. После анализа PostgreSQL обновит pg_class.reltuples, и пороги начнут рассчитываться корректнее.

SELECT reltuples, relpages
FROM pg_class
WHERE relname = 'autovac';

Если затем обновить 31 строку при пороге 30, условие autovacuum выполнится:

UPDATE autovac SET s = 'B' WHERE id <= 31;
SELECT * FROM need_vacuum WHERE tablename = 'public.autovac';

Важная тонкость: append-only таблицы, куда только вставляют строки и не делают UPDATE/DELETE, могут долго не очищаться, потому что n_dead_tup = 0. В результате может не обновляться visibility map, а это мешает эффективному Index Only Scan. Иногда для таких таблиц нужен ручной VACUUM.

Регулирование нагрузки

VACUUM не блокирует обычную работу таблицы, но создаёт I/O-нагрузку. Поэтому он может чередовать работу и ожидание.

Для ручного VACUUM используются:

vacuum_cost_limit
vacuum_cost_delay

По умолчанию:

vacuum_cost_limit = 200
vacuum_cost_delay = 0

Для autovacuum есть собственные параметры:

autovacuum_vacuum_cost_limit
autovacuum_vacuum_cost_delay

Если они равны -1, используются обычные vacuum_cost_limit и vacuum_cost_delay.

На многих системах значение autovacuum_vacuum_cost_delay = 20ms может быть слишком медленным. Часто начинают с 2–10ms, но итог зависит от нагрузки и дисковой подсистемы.

Важно: cost limit распределяется между worker-процессами. Если увеличивать autovacuum_max_workers, но не увеличивать autovacuum_vacuum_cost_limit, общая производительность autovacuum может почти не вырасти.

Память autovacuum

VACUUM использует память для хранения идентификаторов версий строк, которые нужно удалить из индексов.

maintenance_work_mem
autovacuum_work_mem

autovacuum_work_mem задаёт отдельный лимит памяти на worker. По умолчанию -1, то есть используется maintenance_work_mem.

Если памяти мало, VACUUM может несколько раз проходить по индексам. Это увеличивает время очистки и нагрузку на I/O. Обычно лучше подобрать минимальное значение autovacuum_work_mem, при котором повторные проходы по индексам не возникают.

Мониторинг autovacuum

Для текущего прогресса:

SELECT * FROM pg_stat_progress_vacuum;

Для истории и регулярного анализа лучше включить логирование autovacuum:

ALTER SYSTEM SET log_autovacuum_min_duration = 0;
SELECT pg_reload_conf();

Значение 0 логирует все запуски autovacuum. В production часто ставят порог, например 1s, 5s или 10s, чтобы не засорять лог.

Пример полезной информации в логе:

automatic vacuum of table "public.autovac": index scans: 0
pages: 0 removed, 18 remain, 0 skipped due to pins, 0 skipped frozen
tuples: 31 removed, 1000 remain, 0 are dead but not yet removable, oldest xmin: 4040
buffer usage: 78 hits, 0 misses, 0 dirtied
avg read rate: 0.000 MB/s, avg write rate: 0.000 MB/s
system usage: CPU: user: 0.00 s, system: 0.00 s, elapsed: 0.00 s

Что смотреть поддержке:

  • tuples removed — сколько dead tuples удалено;
  • dead but not yet removable — старые версии есть, но их удерживает горизонт транзакций;
  • oldest xmin — кто удерживает очистку;
  • index scans — сколько проходов по индексам было нужно;
  • buffer usage — нагрузка на буферы;
  • elapsed — фактическое время выполнения.

Практические выводы для поддержки

  • Не отключать autovacuum глобально и не выключать track_counts.
  • Для больших таблиц снижать autovacuum_vacuum_scale_factor.
  • Для особо активных таблиц задавать параметры на уровне таблицы.
  • Следить за n_dead_tup, n_mod_since_analyze, last_autovacuum, last_autoanalyze.
  • Если растёт список таблиц, требующих очистки, autovacuum не успевает.
  • Часто лучше снизить порог срабатывания, чем просто увеличивать память.
  • Долгие транзакции и idle in transaction могут мешать очистке сильнее любых настроек autovacuum.

Пример

VACUUM (VERBOSE, ANALYZE) users;

Рекомендация для поддержки: всегда проверять:

  • pg_stat_user_tables
  • n_dead_tup
  • autovacuum activity

6. WAL archive — архивирование журнала предзаписи

Что такое WAL

WAL — Write-Ahead Log, журнал предзаписи PostgreSQL. Он находится в каталоге pg_wal/ внутри каталога данных кластера.

В WAL записываются изменения, которые PostgreSQL вносит в файлы данных. Сначала изменение фиксируется в WAL, и только потом соответствующие страницы данных могут быть записаны на диск.

WAL нужен для:

  • восстановления после аварийного завершения сервера;
  • физической репликации;
  • создания базовых резервных копий;
  • Point-in-Time Recovery — восстановления на момент времени;
  • построения standby-серверов и тёплого резерва.

Зачем нужен WAL archive

Обычный PostgreSQL может перерабатывать старые WAL-сегменты после checkpoint, если они больше не нужны для crash recovery или репликации. Но для надёжного восстановления этого недостаточно.

WAL archive сохраняет каждый завершённый WAL-сегмент во внешнее хранилище до того, как PostgreSQL сможет его переработать.

Это даёт несколько преимуществ:

  • можно восстановить кластер из файловой базовой копии и WAL;
  • копия файловой системы не обязана быть полностью согласованной — WAL replay исправит несогласованность;
  • можно хранить непрерывную цепочку изменений после базовой копии;
  • можно остановить восстановление в нужной точке времени;
  • можно поддерживать тёплый резерв, передавая WAL на другой сервер.

Важно: pg_dump и pg_dumpall не являются частью WAL-архивирования. Это логические копии, они не содержат информации для WAL replay.

WAL-сегменты

PostgreSQL физически делит поток WAL на файлы-сегменты. Обычно размер сегмента — 16 MiB, если другой размер не был задан при initdb.

Имя WAL-сегмента отражает его позицию в WAL-последовательности и timeline.

0000000100001234000055CD

Если архивирование не включено, PostgreSQL может перерабатывать старые сегменты, переименовывая и используя их повторно. При архивировании каждый заполненный сегмент нужно сохранить до переработки.

Настройка архивирования WAL

Для включения WAL archive нужны параметры:

wal_level = replica
archive_mode = on
archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f'

В archive_command используются подстановки:

  • %p — путь к WAL-файлу, который нужно заархивировать;
  • %f — только имя WAL-файла;
  • %% — символ процента.

Пример фактической команды после подстановки:

test ! -f /mnt/server/archivedir/00000001000000A900000065 && \
cp pg_wal/00000001000000A900000065 /mnt/server/archivedir/00000001000000A900000065

Важно: команда архивирования выполняется от имени пользователя, под которым работает PostgreSQL. Архив WAL содержит все изменения данных, поэтому архивное хранилище должно быть защищено правами доступа.

Правила для archive_command

  • Команда должна возвращать 0 только если архивирование действительно успешно.
  • Если команда вернула ненулевой код, PostgreSQL будет повторять попытки.
  • Команда не должна перезаписывать существующий архивный файл с другим содержимым.
  • Если файл уже есть и полностью совпадает, команда может вернуть успех.
  • Если архивирование сломалось, pg_wal/ будет расти.

Критический риск: если архивирование постоянно падает, WAL-сегменты будут накапливаться в pg_wal/. При заполнении диска PostgreSQL может аварийно остановиться.

Для сложной логики лучше использовать скрипт:

archive_command = 'local_backup_script.sh "%p" "%f"'

Скрипт может копировать WAL во внешнее хранилище, сжимать, логировать ошибки, взаимодействовать с backup-системой и мониторингом.

archive_timeout и ручное переключение WAL

archive_command вызывается, когда WAL-сегмент заполнен. Если нагрузка маленькая, между commit и попаданием WAL в архив может пройти много времени.

Чтобы ограничить задержку, можно использовать:

archive_timeout = '1min'

Но слишком маленькое значение приведёт к большому количеству неполных WAL-сегментов в архиве, каждый из которых всё равно будет иметь полный размер сегмента.

Для ручного переключения WAL:

SELECT pg_switch_wal();

Это полезно, если нужно быстрее отправить только что завершённые изменения в архив.

Мониторинг WAL archive

Основное представление:

SELECT * FROM pg_stat_archiver;

Что смотреть:

  • archived_count — сколько файлов успешно заархивировано;
  • last_archived_wal — последний архивированный WAL;
  • last_archived_time — время последнего успеха;
  • failed_count — количество ошибок;
  • last_failed_wal — последний WAL с ошибкой;
  • last_failed_time — время последней ошибки.

Типовой запрос поддержки:

SELECT archived_count,
       last_archived_wal,
       last_archived_time,
       failed_count,
       last_failed_wal,
       last_failed_time
FROM pg_stat_archiver;

Также нужно мониторить размер pg_wal/ и свободное место на диске.

Базовая резервная копия и WAL

Для восстановления через WAL archive нужна базовая резервная копия и непрерывная последовательность WAL-сегментов, начиная не позже момента старта этой копии.

Проще всего создать базовую копию через pg_basebackup:

pg_basebackup -h primary -D /backup/base -X stream -P

Во время создания backup PostgreSQL формирует backup history file. По нему можно понять, какие WAL-сегменты нужны для восстановления.

Практика: интервал между базовыми копиями выбирают по двум ограничениям:

  • сколько места можно выделить под WAL archive;
  • сколько времени допустимо тратить на восстановление и replay WAL.

Низкоуровневый API резервного копирования

Если pg_basebackup не подходит, можно использовать низкоуровневый API:

SELECT pg_backup_start(label => 'daily_backup', fast => false);
-- копирование файлов tar/rsync/cpio
SELECT * FROM pg_backup_stop(wait_for_archive => true);

Важные правила:

  • архивирование WAL должно быть включено и протестировано до начала;
  • соединение с pg_backup_start должно жить до pg_backup_stop;
  • pg_backup_stop может ждать архивации последнего нужного WAL-сегмента;
  • результаты pg_backup_stop важны для файлов backup_label и tablespace_map.

Что исключать из файловой копии

При файловом backup активного кластера важно понимать, что часть каталогов не нужно копировать полностью.

  • pg_wal/ обычно исключают из базовой файловой копии, так как WAL берётся из архива;
  • postmaster.pid и postmaster.opts исключают, чтобы не вводить pg_ctl в заблуждение;
  • pg_replslot/ часто исключают, чтобы не перенести неактуальные replication slots;
  • содержимое pg_dynshmem/, pg_notify/, pg_serial/, pg_snapshots/, pg_stat_tmp/, pg_subtrans/ можно исключать, но сами каталоги должны существовать;
  • временные файлы pgsql_tmp* можно исключать;
  • pg_internal.init можно исключать, он будет перестроен.

Если используются tablespaces, нужно корректно сохранить и восстановить символические ссылки в pg_tblspc/.

Восстановление из WAL archive

Общий порядок восстановления:

  1. Остановить PostgreSQL.
  2. По возможности сохранить текущий каталог данных и табличные пространства.
  3. Очистить целевой каталог данных.
  4. Восстановить файлы из базовой резервной копии.
  5. Очистить pg_wal/ от старых файлов из backup.
  6. Вернуть последние неархивированные WAL, если они были сохранены.
  7. Настроить восстановление через restore_command.
  8. Создать recovery.signal.
  9. Запустить сервер и дождаться replay WAL.
  10. Проверить состояние базы и открыть доступ пользователям.

Минимальная настройка восстановления:

restore_command = 'cp /mnt/server/archivedir/%f %p'

Подстановки такие же:

  • %f — имя нужного WAL-файла;
  • %p — путь, куда PostgreSQL ожидает получить файл.

Команда должна возвращать ненулевой код, если файла нет в архиве. Это нормальная ситуация в конце восстановления.

PITR — восстановление на момент времени

WAL archive позволяет восстановиться не только «до конца», но и до нужного момента времени.

recovery_target_time = '2026-04-25 12:30:00+02'

Точку восстановления можно задавать по:

  • времени;
  • именованной точке восстановления;
  • transaction id, если точно известно, что нужно.

Важно: точка восстановления должна быть позже окончания базовой копии. Нельзя восстановиться из базовой копии на момент, когда она ещё создавалась.

Timeline — линии времени

После завершения восстановления PostgreSQL создаёт новую линию времени. Это нужно, чтобы новая история WAL не перезаписала старую.

В имени WAL-файла первые 8 символов — идентификатор timeline:

00000001 00001234 000055CD

При каждом ответвлении создаётся файл истории timeline. Его нужно архивировать так же, как WAL-сегменты.

Timeline полезны, когда нужно несколько раз пробовать восстановление на разные моменты времени и при этом сохранять возможность вернуться к старым веткам истории.

recovery_target_timeline = 'latest'

Сжатие и скрипты архивирования

Если архив занимает много места, WAL можно сжимать:

archive_command = 'gzip < %p > /mnt/server/archivedir/%f.gz'

Для восстановления:

restore_command = 'gunzip < /mnt/server/archivedir/%f.gz > %p'

Для production лучше использовать скрипты, потому что они позволяют:

  • копировать WAL во внешнее безопасное хранилище;
  • делать повторные попытки;
  • писать понятные логи;
  • отправлять ошибки в мониторинг;
  • работать с S3/NFS/backup-системой.

Если archive_command вызывает скрипт, полезно включить logging_collector, чтобы stderr скрипта попадал в журнал PostgreSQL.

Ограничения и важные замечания

  • WAL archive восстанавливает весь кластер целиком, а не отдельную таблицу.
  • Конфигурационные файлы postgresql.conf, pg_hba.conf, pg_ident.conf не попадают в WAL, их нужно сохранять отдельно.
  • Создание/удаление tablespace требует особой осторожности: пути tablespace записываются в WAL как абсолютные.
  • После операций с tablespace лучше сделать новую базовую копию.
  • Если WAL повреждён, восстановление остановится на повреждённом месте.
  • Если архив временно недоступен, восстановление можно перезапустить после устранения причины.
  • full_page_writes увеличивает объём WAL, но защищает от частичной записи страниц.

Практический чек-лист поддержки

  1. Проверить archive_mode, archive_command, wal_level.
  2. Проверить pg_stat_archiver на ошибки и задержки.
  3. Проверить свободное место в pg_wal/ и архивном хранилище.
  4. Проверить, не копит ли PostgreSQL WAL из-за неработающего archive_command.
  5. Проверить, есть ли базовая копия и непрерывная цепочка WAL после неё.
  6. Проверить, архивируются ли timeline history files.
  7. Для восстановления подготовить restore_command и recovery.signal.
  8. После восстановления проверить данные до открытия доступа пользователям.

7. Репликация PostgreSQL: физическая и логическая

Зачем нужна репликация

Взаимодействие нескольких PostgreSQL-серверов можно организовать по-разному. На практике репликация нужна для:

  • повышения доступности — если основной сервер недоступен, можно перейти на реплику;
  • распределения нагрузки на чтение;
  • создания резервного сервера;
  • миграции и обновления major-версии PostgreSQL;
  • консолидации данных из нескольких источников;
  • построения специальных схем, например отложенной реплики.

В PostgreSQL есть два базовых подхода: физическая и логическая репликация.

Физическая репликация: принцип работы

При физической репликации серверы имеют роли: мастер/primary и реплика/standby. Primary передаёт на реплику журнальные записи WAL — как поток или как файлы. Реплика применяет эти записи к своим файлам данных.

Применение происходит механически, без понимания смысла SQL-команд. Поэтому важна двоичная совместимость между серверами: одинаковая основная версия PostgreSQL, совместимая платформа и окружение.

                WAL stream / WAL archive
Primary ------------------------------------> Replica
 INSERT/UPDATE/DELETE                         continuous recovery
 data files + pg_wal                          data files replay WAL

Поскольку WAL общий для всего кластера, физическая репликация реплицирует весь кластер целиком, а не отдельные таблицы.

Физическая репликация похожа на постоянно восстанавливаемый backup

Настройка физической репликации похожа на физическое резервное копирование:

  • создаётся базовая резервная копия через pg_basebackup;
  • реплика запускается в режиме непрерывного восстановления;
  • сервер восстанавливает согласованность и продолжает применять новые WAL;
  • WAL доставляется потоком по протоколу репликации или через архив WAL.
pg_basebackup  ->  старт реплики  ->  replay WAL  ->  постоянное восстановление

В отличие от обычной резервной копии, реплика поднимается сразу и постоянно догоняет primary. В случае сбоя она уже почти готова принять нагрузку.

Важно: репликация сама по себе не заменяет PITR. Реплика обычно содержит почти текущее состояние, поэтому ошибка пользователя, например случайный DELETE, тоже будет применена на реплике. Для восстановления на произвольный момент нужен backup + WAL archive или отложенная реплика.

Тёплый и горячий резерв

  • Тёплый резерв — реплика применяет WAL, но не принимает пользовательские подключения.
  • Горячий резерв — реплика допускает подключения на чтение после восстановления согласованности.
Warm standby:
Primary -> Replica, подключений нет

Hot standby:
Primary -> Replica, SELECT разрешён

Горячая реплика позволяет разгрузить primary по чтению, но важно учитывать replication lag: данные на реплике могут быть не самыми свежими.

Что можно выполнять на физической реплике

Разрешено:

  • SELECT, COPY TO, курсоры;
  • SET, RESET;
  • BEGIN, COMMIT, ROLLBACK для читающих транзакций;
  • pg_basebackup с реплики.

Не допускается:

  • INSERT, UPDATE, DELETE, TRUNCATE;
  • nextval(), потому что sequence меняет состояние;
  • SELECT FOR UPDATE и другие блокировки, предполагающие изменение;
  • DDL: CREATE, DROP, включая временные таблицы;
  • VACUUM, ANALYZE, REINDEX;
  • GRANT, REVOKE;
  • триггеры и пользовательские advisory locks.

Реплика в hot standby — это сервер для чтения, а не самостоятельный сервер записи.

Потоковая репликация

Основной практический способ доставки WAL — streaming replication. Реплика подключается к primary по протоколу репликации и читает поток WAL-записей почти в реальном времени.

Application
  | SELECT/INSERT/UPDATE/DELETE
  v
Primary PostgreSQL
  | wal sender
  |================ WAL stream ================
  |                                      wal receiver
  v                                           v
pg_wal                                  Replica PostgreSQL
                                       continuous recovery

Процессы:

  • wal sender — на primary, отправляет WAL;
  • wal receiver — на replica, принимает WAL;
  • startup/recovery process — применяет WAL на реплике.

При потоковой репликации задержка обычно минимальна, а в синхронном режиме может быть близка к нулю по подтверждённым транзакциям.

Конфликт VACUUM и запросов на реплике

Тонкий момент физической репликации: на primary VACUUM может удалить версии строк, которые ещё нужны долгому snapshot-запросу на реплике. В таком случае PostgreSQL может отменить запрос на реплике.

Для потоковой репликации существует обратная связь:

hot_standby_feedback = on

Реплика сообщает primary, какой xmin нужен её запросам. Primary откладывает очистку старых версий.

Компромисс: запросы на реплике меньше отменяются, но на primary может расти bloat, потому что VACUUM не может удалить старые версии строк.

Репликация через архив WAL

Второй способ доставки WAL — через архив. Primary архивирует завершённые WAL-сегменты через archive_command, а реплика читает их через restore_command.

Primary
  | archive_command
  v
WAL archive -------------- restore_command --------------> Replica
                                                        replay WAL

Если streaming replication не может получить нужный WAL, реплика может попробовать взять его из архива.

На практике часто используют схему:

streaming replication + WAL archive

Почему это важно:

  • если primary удалит WAL до передачи реплике, реплика сможет взять его из архива;
  • архив WAL всё равно нужен для backup/PITR;
  • это повышает устойчивость репликации.

Репликация может работать только через архив, без streaming, но тогда реплика будет отставать минимум на время заполнения WAL-сегмента. Кроме того, primary не знает о такой реплике, и VACUUM-конфликты сложнее контролировать.

Replication slots

При streaming replication есть риск: primary может удалить WAL-сегмент, который реплика ещё не получила. Один из способов защиты — replication slot.

SELECT * FROM pg_replication_slots;

Slot сообщает primary, какие WAL ещё нужны потребителю. Пока реплика не получит WAL, primary не удалит эти сегменты.

Опасность: если реплика умерла, а slot остался активным, pg_wal/ может бесконечно расти. Поэтому slots обязательно мониторят.

Переключение на реплику: switchover и failover

Причины перехода на реплику бывают разные:

  • Switchover — плановое переключение для технических работ;
  • Failover — аварийное переключение при сбое primary.

В PostgreSQL нет встроенного полноценного cluster manager, который сам принимает решение о failover. Для автоматизации используют Patroni, repmgr, Pacemaker или другие внешние средства.

До переключения:
Primary  --WAL-->  Replica
 write             read only

После promote:
Former Primary     New Primary
 disconnected      write/read

При promote реплика прекращает режим восстановления и становится самостоятельным primary. После этого приложения нужно перенаправить на новый сервер внешними средствами: HAProxy, VIP, DNS, service discovery.

Возврат бывшего primary

После failover бывший primary нельзя просто подключить к новому primary как реплику. Причина: на старом primary могли остаться WAL-записи, которые не успели попасть на бывшую реплику. Если поверх них начать применять WAL с нового primary, можно повредить данные.

Есть варианты:

  • создать новую реплику с нуля через pg_basebackup — надёжно, но долго;
  • rsync — может ускорить пересоздание;
  • pg_rewind — быстро вернуть бывший primary как replica, если условия позволяют.

pg_rewind находит изменения, которые разошлись после общей точки истории, и заменяет затронутые страницы страницами с нового primary. После этого запускается обычное восстановление.

Old Primary --pg_rewind--> Replica of New Primary

Для поддержки важно: после failover всегда проверять timeline, WAL availability и возможность pg_rewind/reinit.

Несколько реплик: HA и распределение чтения

Одна из типовых схем:

                  Primary
                /    |    \
               /     |     \
          Replica A Replica B Replica C
          read only read only read only

Задачи:

  • высокая доступность;
  • распределение SELECT-нагрузки;
  • резервный сервер для аварийного перехода;
  • backup с реплики.

Нужно учитывать: каждой реплике соответствует отдельный wal sender на primary и, при использовании slots, отдельный replication slot. Балансировка чтения между репликами решается внешними средствами.

Синхронная и асинхронная физическая репликация

Асинхронная репликация: primary подтверждает commit, не ожидая реплику. Это быстрее, но при аварии можно потерять последние транзакции.

Синхронная репликация: commit на primary не завершается, пока не получит подтверждение от синхронной реплики.

Transaction commit on Primary:
1. write WAL locally
2. wait for synchronous replica confirmation
3. mark transaction committed

Синхронность повышает надёжность, но увеличивает latency. Ей можно управлять на уровне конфигурации и иногда на уровне транзакций.

Особенность: синхронная реплика может увидеть изменения раньше, чем параллельный запрос на primary, потому что порядок видимости и подтверждения не всегда интуитивен.

Каскадная репликация

Каскадная репликация позволяет не нагружать primary большим количеством реплик. Одна реплика передаёт WAL следующей.

Primary
  |
  v
Replica A
  |
  v
Replica B
  |
  v
Replica C

Плюсы:

  • меньше wal sender-процессов на primary;
  • можно строить географически распределённые схемы;
  • удобно при большом числе реплик.

Минусы:

  • чем дальше реплика от primary, тем больше lag;
  • сложнее мониторинг;
  • при failover лучше выбирать ближайшую к primary и наименее отстающую реплику.

Отложенная репликация

Отложенная реплика применяет WAL не сразу, а с заданной задержкой. Это полезно как «машина времени».

Primary --WAL--> Delayed Replica
              replay delay: 30 minutes

Сценарии:

  • посмотреть данные до ошибочного DELETE/UPDATE;
  • быстрее восстановиться на момент времени без полного PITR;
  • иметь резервную копию состояния «немного в прошлом».

Для корректной работы нужна синхронизация часов между серверами.

Риск: если включён feedback, большая задержка может вызвать bloat на primary, потому что VACUUM будет вынужден сохранять старые версии строк для реплики.

Логическая репликация: принцип работы

Логическая репликация передаёт изменения на уровне строк таблиц. Для этого WAL должен содержать информацию более высокого уровня:

wal_level = logical

Встроенная логическая репликация доступна начиная с PostgreSQL 10. В более ранних версиях использовали pg_logical или триггерные схемы репликации.

Модель работы:

Publisher database
  publication: table_a, table_b
        |
        | logical changes via replication protocol
        v
Subscriber database
  logical replication worker applies rows

В логической репликации нет жёсткой роли «мастер/реплика» на уровне всего сервера. Один сервер может публиковать одни таблицы и подписываться на другие.

Publication / Subscription

На публикующем сервере создаётся публикация. Она включает таблицы одной базы данных. Подписчик создаёт subscription и получает изменения.

CREATE PUBLICATION app_pub FOR TABLE orders, customers;

CREATE SUBSCRIPTION app_sub
CONNECTION 'host=publisher dbname=app user=repl password=secret'
PUBLICATION app_pub;

Реплицируются не SQL-команды, а изменения строк:

  • INSERT;
  • UPDATE;
  • DELETE;
  • в современных версиях PostgreSQL также возможны дополнительные режимы, но базовая идея — передача изменений данных.

DDL не передаётся автоматически. Таблицы на подписчике нужно подготовить заранее или синхронизировать отдельно. При создании подписки возможна начальная синхронизация данных.

Процессы логической репликации

Publisher
  WAL + logical decoding
  wal sender
      |
      v
Subscriber
  logical replication worker
  apply changes

На publisher изменения декодируются из WAL и отправляются по протоколу репликации. На subscriber фоновый процесс logical replication worker принимает изменения и применяет их.

Для надёжности используется logical replication slot, чтобы не терять и не дублировать изменения.

Важно: если подписчик долго недоступен, publisher будет сохранять WAL для logical slot, и это может привести к росту pg_wal/.

Replica identity и конфликты

Для INSERT всё просто: добавляется новая строка. Но для UPDATE и DELETE подписчик должен понять, какую старую строку нужно изменить или удалить.

Для этого используется replica identity:

  • первичный ключ — по умолчанию;
  • уникальный индекс с NOT NULL;
  • все столбцы;
  • без идентификации — для таблиц, где UPDATE/DELETE не должны реплицироваться.
ALTER TABLE orders REPLICA IDENTITY USING INDEX orders_uidx;
ALTER TABLE orders REPLICA IDENTITY FULL;

Конфликты возникают, если на подписчике локальные данные нарушают ограничения при применении изменений. Например, приходит INSERT, а такая строка уже есть.

При конфликте логическая репликация обычно приостанавливается до ручного вмешательства:

  • исправить данные на subscriber;
  • пропустить конфликтующую транзакцию, если это допустимо;
  • пересинхронизировать таблицу.

Сценарий 1: консолидация данных

Несколько региональных серверов публикуют данные, а центральный сервер подписывается на них.

Region A Publisher ----\
                       +--> Central Subscriber
Region B Publisher ----/

Central receives selected tables from branches

Так можно собирать данные филиалов в центральную систему. Обратная схема подходит для распространения справочников из центра в регионы.

Нужно учитывать постоянное соединение: если subscriber недоступен, publisher сохраняет WAL для slot.

Сценарий 2: обновление major-версии без долгого простоя

Физическая репликация не подходит для разных major-версий PostgreSQL, потому что нет двоичной совместимости. Логическая репликация может помочь.

Old PostgreSQL 10  --logical replication-->  New PostgreSQL 11+
       writes                              initial sync + apply changes

Общий подход:

  1. создать новый сервер нужной версии;
  2. создать схемы и объекты;
  3. настроить публикации и подписки;
  4. дождаться начальной синхронизации;
  5. переключить клиентов на новый сервер внешними средствами;
  6. выключить старый сервер после проверки.

На практике такой upgrade сложен: нужно учитывать sequences, DDL, расширения, права, jobs, функции, типы и поведение приложения.

Сценарий 3: master-master и двунаправленные схемы

Логическая репликация теоретически позволяет строить схемы, где несколько серверов принимают запись и обмениваются изменениями.

Server A publication  <---->  subscription Server B
Server A subscription <---->  publication  Server B

Но это не «магический multi-master». Приложение должно предотвращать конфликты: например, разные серверы работают с разными диапазонами ключей или разными наборами данных.

Ограничения:

  • нет глобальных распределённых транзакций;
  • нет автоматического разрешения бизнес-конфликтов;
  • автоматизация отказов и добавления узлов решается внешними средствами;
  • согласованность между серверами требует отдельного проектирования.

Что выбирать на практике

  • Нужен HA и read-only реплики? Физическая репликация.
  • Нужно обновить major-версию с малым простоем? Логическая репликация.
  • Нужно реплицировать часть таблиц? Логическая репликация.
  • Нужен точный standby всего кластера? Физическая репликация.
  • Нужна защита от случайного DELETE? Backup + PITR или delayed replica, а не обычная реплика.
  • Нужно масштабировать чтение? Физические hot standby-реплики.
  • Нужно собирать данные филиалов? Логическая репликация или пакетная интеграция.

Мониторинг репликации

Для физической репликации на primary:

SELECT application_name,
       client_addr,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
FROM pg_stat_replication;

Для replication slots:

SELECT slot_name,
       slot_type,
       active,
       restart_lsn,
       confirmed_flush_lsn
FROM pg_replication_slots;

Для logical subscriptions на подписчике:

SELECT * FROM pg_stat_subscription;

Что смотрит поддержка:

  • растёт ли replication lag;
  • не завис ли wal receiver;
  • не удерживает ли slot старые WAL;
  • есть ли ошибки apply worker;
  • не отличается ли timeline после failover;
  • не растёт ли pg_wal/.

Главные выводы

  • Физическая репликация передаёт WAL и создаёт точную копию всего кластера.
  • Физическая репликация однонаправленная и требует двоичной совместимости.
  • Логическая репликация передаёт изменения строк отдельных таблиц.
  • Логическая репликация гибче, но требует проектирования схемы, ключей, DDL и обработки конфликтов.
  • Репликация не заменяет backup: ошибка пользователя может быстро попасть на реплики.
  • Для production обычно нужны вместе: репликация, WAL archive, backup, мониторинг и процедура восстановления.

8. EXPLAIN ANALYZE — подробный разбор планов запросов

Зачем нужен EXPLAIN

При выполнении любого SQL-запроса PostgreSQL сначала строит план выполнения. Планировщик решает, как читать таблицы, какие индексы использовать, каким способом соединять таблицы, когда сортировать данные и где можно остановить выполнение раньше, например из-за LIMIT.

Правильный план критически важен для производительности. Один и тот же запрос может выполняться миллисекунды или минуты в зависимости от выбранного плана.

EXPLAIN SELECT * FROM orders WHERE id = 100;
EXPLAIN ANALYZE SELECT * FROM orders WHERE id = 100;

EXPLAIN показывает ожидаемый план без выполнения запроса. EXPLAIN ANALYZE выполняет запрос реально и показывает фактические метрики.

Для автоматической обработки можно использовать форматы JSON, YAML или XML:

EXPLAIN (FORMAT JSON) SELECT * FROM orders;
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT * FROM orders;

План запроса как дерево узлов

План запроса — это дерево. Нижние узлы обычно читают данные: таблицы, индексы, результаты функций или VALUES. Верхние узлы выполняют операции над полученными строками: сортировку, агрегацию, соединение, фильтрацию, ограничение количества строк.

Seq Scan on tenk1  (cost=0.00..445.00 rows=10000 width=244)

В этом примере выбран Seq Scan — последовательное сканирование всей таблицы. Такой план нормален, если нужно прочитать большую часть таблицы или если таблица маленькая.

Отступы в выводе EXPLAIN показывают вложенность: дочерние узлы передают строки родительским узлам.

cost, rows, width

В скобках EXPLAIN показывает оценки планировщика:

  • startup cost — стоимость до начала выдачи первых строк;
  • total cost — стоимость выполнения узла до конца;
  • rows — сколько строк узел должен вернуть наружу;
  • width — средний размер возвращаемой строки в байтах.
Seq Scan on tenk1  (cost=0.00..470.00 rows=7000 width=244)
  Filter: (unique1 < 7000)

Важно: rows — это не количество прочитанных строк, а количество строк после фильтрации. Узел может прочитать 10000 строк, но вернуть 7000.

Стоимость измеряется не в миллисекундах, а в условных единицах планировщика. Обычно за базу берётся стоимость чтения страницы с диска. Верхний узел включает стоимость дочерних узлов.

Seq Scan, Index Scan и Bitmap Scan

Seq Scan читает таблицу целиком. Это не всегда плохо: если таблица маленькая или нужно много строк, последовательное чтение может быть быстрее индекса.

EXPLAIN SELECT * FROM tenk1 WHERE unique1 < 7000;

Index Scan эффективен, когда нужно мало строк или когда порядок индекса помогает выполнить ORDER BY.

Index Scan using tenk1_unique1 on tenk1
  Index Cond: (unique1 = 42)

Bitmap Index Scan + Bitmap Heap Scan часто используется, когда строк больше, чем для обычного Index Scan, но меньше, чем для полного сканирования таблицы.

Bitmap Heap Scan on tenk1
  Recheck Cond: (unique1 < 100)
  -> Bitmap Index Scan on tenk1_unique1
       Index Cond: (unique1 < 100)

Bitmap-план сначала находит адреса строк в индексе, затем читает страницы таблицы более упорядоченно.

Index Cond, Filter, Recheck Cond

Bitmap Heap Scan on tenk1
  Recheck Cond: (unique1 < 100)
  Filter: (stringu1 = 'xxx')
  -> Bitmap Index Scan on tenk1_unique1
       Index Cond: (unique1 < 100)
  • Index Cond — условие реально используется индексом;
  • Filter — условие проверяется после получения строк;
  • Recheck Cond — повторная проверка условия после bitmap/index этапа.

Если важный предикат оказался в Filter, а не в Index Cond, возможно, нужен другой индекс или составной индекс.

ORDER BY, Sort и Incremental Sort

ORDER BY может выполняться несколькими способами:

  • через порядок уже существующего индекса;
  • через отдельный узел Sort;
  • через Incremental Sort, если часть порядка уже обеспечена нижним узлом.
Sort  (cost=1109.39..1134.39 rows=10000 width=244)
  Sort Key: unique1
  -> Seq Scan on tenk1
Limit
  -> Incremental Sort
       Sort Key: hundred, ten
       Presorted Key: hundred
       -> Index Scan using tenk1_hundred on tenk1

Incremental Sort может начать выдавать строки раньше полной сортировки и часто полезен вместе с LIMIT. Но он тоже имеет накладные расходы.

Комбинирование индексов: BitmapAnd и BitmapOr

Если условия используют разные индексы, планировщик может объединить результаты через BitmapAnd или BitmapOr.

Bitmap Heap Scan on tenk1
  Recheck Cond: ((unique1 < 100) AND (unique2 > 9000))
  -> BitmapAnd
       -> Bitmap Index Scan on tenk1_unique1
       -> Bitmap Index Scan on tenk1_unique2

Это не всегда выгоднее одного индекса плюс Filter: нужно обойти несколько индексов, и стоимость может оказаться выше.

LIMIT и ранняя остановка

LIMIT может полностью изменить план. Планировщик может выбрать путь, который быстро найдёт первые строки, даже если полное выполнение этого пути было бы дороже.

Limit
  -> Index Scan using tenk1_unique2 on tenk1
       Index Cond: (unique2 > 9000)
       Filter: (unique1 < 100)

Оценки дочернего узла могут быть рассчитаны как будто он выполнится до конца, но фактически Limit остановит чтение раньше. Это не ошибка планировщика.

Типы соединений: Nested Loop, Hash Join, Merge Join

Nested Loop выполняет внутренний узел для каждой строки внешнего узла. Хорош, если внешних строк мало, а внутренний поиск идёт по индексу.

Nested Loop
  -> Bitmap Heap Scan on tenk1
  -> Index Scan using tenk2_unique2 on tenk2

Hash Join строит хеш-таблицу по одной стороне соединения и затем проверяет строки другой стороны.

Hash Join
  Hash Cond: (t2.unique2 = t1.unique2)
  -> Seq Scan on tenk2 t2
  -> Hash
       -> Bitmap Heap Scan on tenk1 t1

Merge Join требует отсортированных входных потоков. Он эффективен, если данные уже идут в нужном порядке из индексов или если сортировка стоит недорого.

Merge Join
  Merge Cond: (t1.unique2 = t2.unique2)
  -> Index Scan using tenk1_unique2 on tenk1 t1
  -> Index Scan using onek_unique2 on onek t2

Join Filter применяется в узле соединения, если условие зависит от обеих таблиц. Во внешних соединениях Join Filter и обычный Filter ведут себя по-разному: Join Filter может оставить строку с NULL-расширением, а обычный Filter полностью исключает строку.

Materialize

Узел Materialize сохраняет промежуточный результат в памяти, чтобы не перечитывать его заново много раз.

Nested Loop
  -> Bitmap Heap Scan on tenk1
  -> Materialize
       -> Index Scan using tenk2_unique2 on tenk2

Это часто появляется, когда внутренний результат во вложенном цикле нужно использовать несколько раз.

SubPlan, hashed SubPlan и InitPlan

Подзапросы могут превращаться в отдельные подпланы.

  • SubPlan может выполняться для каждой строки внешнего запроса;
  • hashed SubPlan выполняется один раз и сохраняет результат в хеш-таблице;
  • InitPlan выполняется один раз до основного плана, если подзапрос не зависит от внешних строк и возвращает одно значение.
Filter: (NOT (ANY (unique1 = (hashed SubPlan 1).col1)))

Для поддержки важно замечать SubPlan, который выполняется много раз: он может быть причиной медленного запроса.

EXPLAIN ANALYZE: actual time, rows, loops

EXPLAIN ANALYZE добавляет фактические данные выполнения.

Index Scan using tenk2_unique2 on tenk2
  (cost=0.29..7.90 rows=1 width=244)
  (actual time=0.003..0.003 rows=1 loops=10)
  • actual time — фактическое время в миллисекундах;
  • actual rows — фактическое число строк на выходе узла;
  • loops — сколько раз узел был выполнен.

Если loops больше 1, actual time и rows обычно показываются как среднее за один цикл. Чтобы грубо оценить суммарное время узла, нужно умножить время на loops.

Главный сигнал проблемы: estimated rows сильно отличаются от actual rows. Например, планировщик ожидал 10 строк, а получил 500000.

BUFFERS и ввод-вывод

Параметр BUFFERS показывает, как запрос работал с буферами.

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE id = 10;
  • shared hit — страницы найдены в shared buffers;
  • shared read — страницы прочитаны с диска;
  • dirtied — страницы стали грязными;
  • written — страницы записаны.

Много shared read может означать холодный кеш или нагрузку на диск. Много dirtied/written важно для UPDATE/DELETE/INSERT.

Если вывод BUFFERS не нужен:

EXPLAIN (ANALYZE, BUFFERS OFF) SELECT * FROM orders;

Sort Method, Hash Batches, Index Searches

Для некоторых узлов EXPLAIN ANALYZE показывает расширенную статистику.

Sort Method: quicksort  Memory: 74kB
Buckets: 1024  Batches: 1  Memory Usage: 35kB
Index Searches: 4
  • Sort Method показывает метод сортировки и память; если сортировка ушла на диск, стоит проверить work_mem;
  • Hash Batches больше 1 может означать, что хеш-таблица не поместилась в память;
  • Index Searches показывает количество поисков по индексу, полезно для IN, skip scan и повторных проходов.

Rows Removed by Filter / Index Recheck

Seq Scan on tenk1
  Filter: (ten < 7)
  Rows Removed by Filter: 3000

Rows Removed by Filter показывает, сколько строк было отброшено фильтром после чтения. Большое значение часто означает, что запрос читает слишком много лишнего.

Rows Removed by Index Recheck: 1

Rows Removed by Index Recheck часто встречается у неточных индексов, например GiST: индекс возвращает кандидатов, а точная проверка отбрасывает лишние строки.

Безопасный анализ UPDATE / DELETE / INSERT / MERGE

EXPLAIN ANALYZE действительно выполняет запрос. Поэтому для изменяющих команд используйте транзакцию и ROLLBACK.

BEGIN;
EXPLAIN ANALYZE UPDATE tenk1 SET hundred = hundred + 1 WHERE unique1 < 100;
ROLLBACK;

В планах UPDATE/DELETE/MERGE верхний узел обычно отвечает за изменение данных, а дочерние узлы ищут строки. Время самого изменения может быть значительным, но не всегда отражается в cost так же, как чтение.

Planning Time и Execution Time

  • Planning Time — время построения и оптимизации плана;
  • Execution Time — время выполнения плана, включая запуск/остановку исполнителя и триггеры, но не включая разбор SQL и переписывание запроса.

Время верхнего узла не включает отправку данных клиенту. Поэтому реальное время в приложении может быть больше, особенно если результат большой или сеть медленная.

Ограничения EXPLAIN ANALYZE

  • EXPLAIN ANALYZE добавляет собственные накладные расходы на измерения;
  • данные не отправляются клиенту, поэтому сетевые задержки обычно не учитываются;
  • на маленькой тестовой таблице план может быть совсем другим, чем на production;
  • LIMIT может остановить дочерний узел раньше, чем предполагает его оценка;
  • Merge Join может не читать один из входов до конца;
  • BitmapAnd и BitmapOr могут показывать actual rows = 0 из-за особенностей реализации;
  • для секционированных таблиц часть подпланов может быть удалена во время выполнения: Subplans Removed.

Практический чек-лист поддержки

  1. Получить точный SQL и параметры, с которыми он выполнялся.
  2. Проверить, можно ли безопасно запускать EXPLAIN ANALYZE.
  3. Для SELECT использовать EXPLAIN (ANALYZE, BUFFERS).
  4. Для UPDATE/DELETE/INSERT запускать внутри BEGIN и завершать ROLLBACK.
  5. Сравнить estimated rows и actual rows.
  6. Найти узлы с большим временем и большим loops.
  7. Проверить, не попали ли важные условия в Filter вместо Index Cond.
  8. Проверить Sort Method, Hash Batches, temp files и work_mem.
  9. Проверить shared read, если есть подозрение на дисковую проблему.
  10. Если статистика устарела — предложить ANALYZE.
  11. Если нужен индекс или переписывание SQL — передать DBA/разработчикам SQL и полный план.

9. Мониторинг сервера и экземпляра

Что нужно мониторить

Мониторинг PostgreSQL должен охватывать не только сам экземпляр БД, но и операционную систему, диск, репликацию, autovacuum, WAL archive и пользовательские сессии.

Главная цель поддержки: быстро понять, проблема в SQL, блокировках, диске, памяти, репликации, WAL archive или инфраструктуре.

Мониторинг ОС

  • CPU: load average, steal time, saturation;
  • RAM: свободная память, page cache, swap;
  • Disk: IOPS, latency, queue, utilisation;
  • Filesystem: свободное место, inode, рост каталогов pg_wal/, backup и archive;
  • Network: потери, задержки, пропускная способность между primary/replica и backup-хранилищем.
top
vmstat 1
iostat -xz 1
df -h
du -sh $PGDATA/pg_wal

Мониторинг сессий и запросов

Хотя отдельный раздел pg_stat_activity удалён, само представление остаётся ключевым инструментом диагностики.

SELECT pid,
       usename,
       application_name,
       client_addr,
       state,
       wait_event_type,
       wait_event,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

Что искать:

  • idle in transaction — удерживает снимок, мешает VACUUM;
  • долгие активные запросы;
  • ожидания по Lock, IO, Client;
  • много подключений от одного приложения;
  • транзакции с большим xact_age.

Мониторинг WAL archive

WAL archive критичен для PITR, восстановления из базовой копии и непрерывной цепочки изменений. Если архивирование ломается, каталог pg_wal/ начинает расти и может заполнить диск.

SELECT archived_count,
       last_archived_wal,
       last_archived_time,
       failed_count,
       last_failed_wal,
       last_failed_time
FROM pg_stat_archiver;

Контролировать нужно:

  • archive_command — успешно ли выполняется;
  • failed_count — растёт ли число ошибок;
  • last_archived_time — не устарело ли время последней успешной архивации;
  • размер pg_wal/;
  • свободное место в архивном хранилище;
  • наличие непрерывной WAL-цепочки после последней базовой копии;
  • архивируются ли timeline history files.
SHOW archive_mode;
SHOW archive_command;
SHOW archive_timeout;
SELECT pg_switch_wal();

Аварийный признак: failed_count растёт, last_archived_time старое, а pg_wal/ увеличивается. Это означает, что WAL не уходит в архив и есть риск заполнения диска.

Мониторинг backup / restore / PITR

Для восстановления через WAL archive недостаточно просто иметь WAL. Нужны:

  • актуальная базовая резервная копия;
  • непрерывная цепочка WAL после неё;
  • рабочий restore_command;
  • понятная точка восстановления;
  • проверенный restore drill.

Что проверять поддержке:

  • когда была последняя базовая копия;
  • есть ли WAL с момента старта/окончания этой копии;
  • сколько времени займёт replay WAL;
  • достаточно ли места для восстановления;
  • проводился ли тестовый restore.
restore_command = 'cp /mnt/server/archivedir/%f %p'
recovery_target_time = '2026-04-25 12:30:00+02'
recovery_target_timeline = 'latest'

Мониторинг репликации

SELECT application_name,
       client_addr,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
FROM pg_stat_replication;

Что важно:

  • реплика отстаёт или нет;
  • растёт ли lag;
  • есть ли проблемы сети между primary и replica;
  • не удерживает ли replication slot старые WAL;
  • совпадает ли timeline после failover.

Мониторинг autovacuum и bloat

Мониторинг блокировок

SELECT blocked.pid AS blocked_pid,
       blocked.query AS blocked_query,
       blocking.pid AS blocking_pid,
       blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_locks blocked_locks ON blocked_locks.pid = blocked.pid
JOIN pg_locks blocking_locks
  ON blocking_locks.locktype = blocked_locks.locktype
 AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
 AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
 AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
 AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
 AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
 AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
 AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
 AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
 AND blocking_locks.pid <> blocked_locks.pid
JOIN pg_stat_activity blocking ON blocking.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;

Особое внимание:

  • кто блокирует production-запросы;
  • есть ли долгий DDL;
  • нет ли ACCESS EXCLUSIVE;
  • нет ли цепочки блокировок.

Типовые аварии и первые действия

  • Диск почти заполнен → проверить pg_wal/, архив WAL, temp files, backup.
  • База тормозит → проверить CPU, IO latency, долгие запросы, блокировки, autovacuum.
  • Растёт WAL → проверить pg_stat_archiver, replication slots, replica lag.
  • Реплика отстаёт → проверить сеть, IO на replica, long-running query на replica, slots.
  • VACUUM не чистит → проверить backend_xmin, idle in transaction, long transactions.
  • Ошибки PITR/restore → проверить restore_command, непрерывность WAL, timeline, recovery target.

10. Практические инциденты

Production troubleshooting

Практический тренажёр для сотрудников поддержки и сопровождения. Каждый сценарий построен по схеме: инцидент → симптомы → гипотезы → команды диагностики → правильное действие → что нельзя делать → итоговый разбор.

Правило drill-mode: сначала собираем факты, затем выбираем минимально рискованное действие. Не удаляем файлы, не перезапускаем сервис и не завершаем сессии без понимания причины.

1. Инцидент: pg_wal заполняет диск

Симптомы: файловая система с PGDATA или pg_wal занята на 90–100%, приложение получает ошибки записи, WAL-сегменты быстро появляются и не удаляются.

Гипотезы: сломан archive_command, отстаёт реплика, replication slot удерживает WAL, резко вырос объём записи, archiver не успевает.

Команды диагностики:

df -h
du -sh $PGDATA/pg_wal

SELECT archived_count, last_archived_wal, last_archived_time,
       failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;

SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

Правильное действие: восстановить archiving, проверить лаг реплик и слоты, удалить только подтверждённо неиспользуемый слот, временно расширить диск при риске остановки сервера.

Что нельзя делать: вручную удалять файлы из pg_wal, удалять все replication slots подряд, считать max_wal_size решением проблемы удержания WAL.

Итоговый разбор: PostgreSQL не удаляет WAL, пока он нужен для архивации, репликации или слота. Важно устранить причину удержания, а не просто освободить место.

Drill-вопрос

1. pg_wal растёт, archive_command успешен, но есть inactive slot с retained 120 GB. Что делать?

2. Инцидент: реплика отстаёт на 2 часа

Симптомы: read-only запросы на реплике показывают старые данные, monitoring показывает большой replay/write/flush lag, на primary растёт WAL.

Гипотезы: медленный диск на реплике, сеть, долгие запросы на replica конфликтуют с recovery, высокая генерация WAL на primary, недостаточные ресурсы replay.

Команды диагностики:

SELECT application_name, client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- На реплике:
SELECT now() - pg_last_xact_replay_timestamp() AS replica_delay;
SELECT * FROM pg_stat_wal_receiver;

Правильное действие: разделить network lag и replay lag, проверить IOPS на реплике, конфликтующие запросы, slots и архив, при необходимости временно снять read-нагрузку с реплики.

Что нельзя делать: blindly promote отстающую реплику, игнорировать lag при read-scaling, удалять WAL на primary.

Итоговый разбор: лаг может быть на передаче, записи, flush или replay. Лечение зависит от стадии, где копится задержка.

3. Инцидент: всё зависло из-за блокировки

Симптомы: множество UPDATE/INSERT/ALTER ожидают, приложение зависает, CPU может быть низким, но запросы не завершаются.

Гипотезы: одна транзакция держит lock, DDL ждёт/держит ACCESS EXCLUSIVE, idle in transaction удерживает row/table lock.

Команды диагностики:

SELECT a.pid, a.usename, a.state, a.wait_event_type, a.wait_event,
       now() - a.xact_start AS xact_age,
       pg_blocking_pids(a.pid) AS blocking_pids,
       a.query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
   OR a.wait_event_type = 'Lock'
ORDER BY xact_age DESC NULLS LAST;

Правильное действие: найти blocker, оценить бизнес-риск, связаться с владельцем, завершить точечно pg_cancel_backend или pg_terminate_backend.

Что нельзя делать: убивать все сессии подряд, запускать новые DDL, перезапускать кластер без анализа.

Итоговый разбор: при блокировках важен не самый долгий blocked-запрос, а корневой blocker.

4. Инцидент: CPU 100% из-за плохого плана

Симптомы: CPU на PostgreSQL стабильно 90–100%, активны однотипные SELECT, latency выросла после релиза или изменения данных.

Гипотезы: seq scan вместо index scan, устаревшая статистика, изменилось распределение данных, не хватает индекса, неверный join order.

Команды диагностики:

SELECT pid, now()-query_start AS age, wait_event_type, query
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY query_start;

SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC;

Правильное действие: обновить статистику, проверить план, добавить индекс CONCURRENTLY при необходимости, временно ограничить проблемный запрос.

Что нельзя делать: сразу увеличивать CPU как единственное решение, делать CREATE INDEX без CONCURRENTLY на большой production-таблице, запускать EXPLAIN ANALYZE для тяжёлого UPDATE без транзакции.

5. Инцидент: autovacuum не успевает

Гипотезы: scale_factor слишком большой для крупной таблицы, workers заняты, cost delay слишком высокий, long transactions удерживают xmin, autovacuum отключён на таблице.

Команды диагностики:

SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, autovacuum_count

FROM pg_class
WHERE reloptions::text ILIKE '%autovacuum%';

Правильное действие: настроить per-table autovacuum, уменьшить scale_factor, проверить long transactions, увеличить ресурсы autovacuum осознанно.

Что нельзя делать: отключать autovacuum глобально, лечить всё только VACUUM FULL, игнорировать idle in transaction.

Итоговый разбор: для больших таблиц дефолтные 20% могут быть слишком большим порогом; autovacuum должен стартовать раньше.

6. Инцидент: wraparound warning

Симптомы: в логах предупреждения про transaction ID wraparound, база может начать запрещать изменения.

Гипотезы: autovacuum не смог заморозить старые XID, долгие транзакции, отключенный autovacuum, слишком старый datfrozenxid.

Что нельзя делать: игнорировать warning, отключать autovacuum, ждать планового окна без оценки возраста XID.

Итоговый разбор: wraparound — критический риск доступности. PostgreSQL защищается, вплоть до запрета операций записи.

Симптомы: новые подключения получают FATAL: too many connections, приложение нестабильно, много idle-сессий.

Гипотезы: нет pooler, утечка соединений, слишком большой пул в приложении, много idle in transaction, не хватает reserved connections для админов.

Команды диагностики:

SELECT state, count(*)

ORDER BY count(*) DESC;

Что нельзя делать: просто бесконечно увеличивать max_connections, убивать системные процессы, не оставлять админский доступ.

Итоговый разбор: каждое соединение потребляет память и процесс. В production чаще нужен pooling, а не огромный max_connections.

Симптомы: приложение получает ERROR: deadlock detected, одна из транзакций прерывается PostgreSQL.

Что нельзя делать: считать deadlock проблемой только БД, отключать проверки, бесконечно увеличивать timeout.

Итоговый разбор: deadlock — это цикл ожидания. PostgreSQL сам разрывает цикл, но приложение должно корректно повторить транзакцию.

9. Инцидент: checkpoint storm / IOPS spike

Симптомы: резкие пики записи на диск, latency растёт волнами, в логах частые checkpoints или checkpoint happens too often.

Гипотезы: слишком маленький max_wal_size, частые checkpoint, большой объём dirty pages, медленный storage.

Команды диагностики:

SELECT checkpoints_timed, checkpoints_req,

       buffers_checkpoint

SHOW checkpoint_completion_target;
SHOW max_wal_size;

Правильное действие: увеличить max_wal_size осознанно, настроить checkpoint_timeout/completion_target, оценить storage и профиль записи.

Что нельзя делать: отключать fsync, игнорировать storage latency, менять параметры без мониторинга WAL и восстановления.

Итоговый разбор: checkpoint storm часто проявляется как регулярные I/O пики. Цель — распределить запись плавнее и дать WAL достаточно пространства.

11. Диагностика и самопроверка

DBA readiness checklist

Этот раздел нужен для самостоятельной проверки реального PostgreSQL-кластера. Ответы лучше фиксировать как mini-runbook: что проверено, какой результат, где настроен мониторинг и кто владелец действия.

Правило: не ограничивайтесь ответом «да/нет». Для каждого пункта укажите SQL-команду, текущие значения, пороги мониторинга и ожидаемую реакцию поддержки.

1. Autovacuum

Проверь свой PostgreSQL-кластер: включён ли autovacuum и какие у него параметры.

SHOW autovacuum;
SHOW track_counts;
SHOW autovacuum_naptime;
SHOW autovacuum_max_workers;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_analyze_threshold;
SHOW autovacuum_analyze_scale_factor;
SHOW autovacuum_vacuum_cost_limit;
SHOW autovacuum_vacuum_cost_delay;

Что зафиксировать: включён ли autovacuum, не отключён ли он на отдельных таблицах, какие таблицы имеют высокий n_dead_tup, когда был последний autovacuum.

2. Replication slots

Проверь, какие слоты есть в кластере и мониторится ли их распухание.

SELECT slot_name, slot_type, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
ORDER BY slot_name;

Что зафиксировать: владелец каждого слота, активность, допустимый retained WAL, алерт по росту, процедура удаления неиспользуемого слота.

3. Уровень изоляции

Проверь, какой уровень изоляции используется в кластерах и почему выбран именно он.

SHOW default_transaction_isolation;

SELECT datname, usename, application_name, state,
       backend_xid, backend_xmin, query
FROM pg_stat_activity
WHERE state <> 'idle';

Что зафиксировать: дефолтный уровень, есть ли приложения с REPEATABLE READ или SERIALIZABLE, реализован ли retry для serialization failure.

4. Блокировки и долгие транзакции

Проверь, настроено ли оповещение по блокировкам транзакций и как в твоём кластере проверяются долгие транзакции.

SELECT pid, usename, application_name, client_addr, state,
       wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       pg_blocking_pids(pid) AS blocking_pids,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

SELECT pid, pg_blocking_pids(pid), query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Что зафиксировать: пороги алертов по lock wait и idle in transaction, кто получает уведомление, когда допустимо применять pg_cancel_backend или pg_terminate_backend.

5. Базы данных и логические лимиты

SELECT datname, datallowconn, datconnlimit

ORDER BY datname;

SHOW max_connections;

SELECT datname, count(*) AS connections

ORDER BY connections DESC;

Что зафиксировать: лимиты подключений по БД и ролям, наличие pooler, reserved connections для администрирования, распределение нагрузки по приложениям.
