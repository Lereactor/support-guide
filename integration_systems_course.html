Курс: Основы интеграции систем

Курс предназначен для прикладных администраторов сопровождения, которые поддерживают интеграции между информационными системами и сервисами. Разбираем четыре основных способа взаимодействия: Kafka, RabbitMQ, ArtemisMQ и REST.

REST

🌐 Синхронный вызов

Сервис вызывает сервис и ждёт ответ. Важно понимать timeout, retry, HTTP-коды и идемпотентность.

Kafka

🟣 Поток событий

Высокая пропускная способность, топики, партиции, consumer groups, offset и replay.

RabbitMQ / ArtemisMQ

📨 Очереди сообщений

Очереди, маршрутизация, ack/nack, DLQ, TTL, redelivery и гарантия доставки.

Главная идея: интеграция — это договор между системами о формате данных, способе передачи, правилах доставки, обработке ошибок и ответственности при сбоях.

1. Что такое интеграция систем

Определение

Интеграция информационных систем — это организованный обмен данными и командами между приложениями. Система-источник формирует событие, запрос или сообщение, а система-получатель принимает его, проверяет, обрабатывает и меняет своё состояние.

Система A -> канал интеграции -> Система B
Источник -> транспорт -> получатель -> обработка -> результат

Что важно сопровождению

  1. Кто источник и кто получатель.
  2. Синхронная или асинхронная интеграция.
  3. Где лежит контракт: OpenAPI, AsyncAPI, JSON Schema, Avro, XSD.
  4. Какие есть очереди, топики, exchange, consumer groups.
  5. Что происходит при ошибке: retry, DLQ, компенсация, ручной разбор.
  6. Какие метрики и логи показывают здоровье интеграции.

4. Интеграции в Kubernetes

Как это выглядит

Pod producer -> Service/DNS -> Broker или REST API -> Pod consumer
ConfigMap/Secret -> адреса, логины, пароли, имена топиков/очередей
Deployment/HPA -> количество обработчиков
Readiness/Liveness -> исключение неготовых экземпляров

В Kubernetes интеграционные параметры обычно вынесены в ConfigMap и Secret: адреса bootstrap servers, URL REST API, имена очередей, топиков, exchange, routing key, username/password, TLS-настройки.

Что проверять в Kubernetes

  1. Запущены ли producer и consumer Pods.
  2. Не растут ли рестарты и CrashLoopBackOff.
  3. Доступен ли broker/API по DNS и порту из Pod.
  4. Правильно ли заданы переменные окружения.
  5. Есть ли HPA для consumer при росте очереди или lag.
  6. Не блокируют ли NetworkPolicy или service mesh исходящие вызовы.
kubectl get pods -n <ns>
kubectl logs deploy/<app> -n <ns>
kubectl exec -it <pod> -n <ns> -- sh
nslookup <broker-service>
curl -vk http://<service>/actuator/health

5. REST-интеграция

Что такое REST-интеграция

REST — это синхронная интеграция поверх HTTP. Один сервис вызывает endpoint другого сервиса и ждёт ответ. REST хорошо подходит для онлайн-сценариев: получить данные клиента, проверить статус заявки, создать сущность, изменить параметры или удалить ресурс.

Для прикладной поддержки важно помнить: REST-запрос — это не просто URL. Это контракт между системами: HTTP-метод, path, query parameters, headers, body, формат ответа, коды ошибок, timeout, retry и правила авторизации.

Client service
   |
   | HTTP request: GET /api/customers/123
   v
Server service
   |
   | HTTP response: 200 OK + JSON body
   v
Client service
Главная особенность REST: вызывающая система ждёт ответ здесь и сейчас. Если downstream-сервис медленный или недоступен, проблема быстро влияет на пользователя или бизнес-операцию.

HTTP-коды ответов: что они значат для сопровождения

КлассЧто означаетКак читать при инциденте
1xx InformationalИнформационные промежуточные ответы. Сервер сообщает, что запрос принят в обработку или можно продолжать передачу.В прикладных логах встречаются редко. Обычно важны для инфраструктуры, прокси, gateway и низкоуровневой HTTP-диагностики.
2xx SuccessЗапрос успешно принят и обработан.Смотреть не только код 200, но и бизнес-результат в теле ответа.
3xx RedirectionПеренаправление. Клиенту нужно обратиться по другому адресу или использовать кэш.Важно при проблемах с gateway, ingress, reverse proxy, балансировщиком, TLS и изменением URL.
4xx Client ErrorОшибка на стороне клиента запроса: данные, авторизация, права, формат, ресурс.Часто означает проблему контракта, токена, прав, обязательных полей или бизнес-валидации.
5xx Server ErrorОшибка на стороне вызываемого сервиса или его зависимостей.Проверять логи сервиса-получателя, БД, внешние системы, thread pool, connection pool, downstream timeout.

Подробно про 1xx и 3xx

КодНазваниеЧто значитЧто важно поддержке
100ContinueКлиент может продолжать отправку тела запроса.Может встречаться при больших POST/PUT-запросах. Если есть проблемы с загрузкой больших payload, смотреть proxy/gateway и ограничения размера body.
101Switching ProtocolsСервер согласился переключить протокол.Актуально для WebSocket/upgrade-сценариев. Для обычного REST почти не используется.
102ProcessingСервер обрабатывает запрос, но финального ответа ещё нет.Редкий код. Может быть полезен для долгих операций, но в большинстве REST API не применяется.
301Moved PermanentlyРесурс постоянно переехал на другой URL.После изменения маршрутов клиенты могут продолжать ходить на старый endpoint. Проверять конфигурацию клиента, gateway и документацию API.
302FoundВременное перенаправление.Может неожиданно появиться из-за SSO, reverse proxy или балансировщика. Для backend-to-backend REST это часто симптом неверной авторизации или маршрута.
304Not ModifiedРесурс не изменился, клиент может использовать кэш.Важно при кэшировании. Если пользователь видит старые данные, проверить Cache-Control, ETag, If-None-Match, CDN/proxy.
307Temporary RedirectВременный redirect с сохранением HTTP-метода.Безопаснее 302 для POST/PUT, потому что метод не должен измениться на GET.
308Permanent RedirectПостоянный redirect с сохранением HTTP-метода.Используется при постоянной миграции endpoint. Проверять, поддерживает ли клиент redirect и не ломается ли авторизация.
Практическое правило: в интеграциях service-to-service 3xx часто нежелательны. Лучше, чтобы сервис сразу ходил на правильный внутренний URL, а не зависел от redirect-логики клиента.

Основные HTTP-методы: GET, POST, PUT, DELETE

МетодНазначениеИдемпотентностьПримерЧто проверять поддержке
GETПолучить ресурс или список ресурсов.Да. Повторный GET не должен менять состояние.GET /api/customers/123Query parameters, права на чтение, кэш, корректность ID, 404 если ресурс не найден.
POSTСоздать ресурс или запустить операцию.Обычно нет. Повторный POST может создать дубль.POST /api/ordersIdempotency-Key, защита от дублей, обязательные поля, бизнес-валидация, 409 при конфликте.
PUTПолностью заменить ресурс или установить состояние по известному ID.Да, если реализован корректно. Повторный PUT приводит к тому же состоянию.PUT /api/customers/123Полное тело объекта, версия ресурса, optimistic lock, 404/409, не затираются ли поля null-значениями.

Что важно настроить

  • Connect timeout — сколько ждём установления соединения.
  • Read timeout — сколько ждём ответ после отправки запроса.
  • Retry — повторять только безопасные или идемпотентные операции. Для POST нужна защита от дублей.
  • Circuit breaker — временно прекращать вызовы в падающую систему, чтобы не усиливать аварию.
  • Rate limiter — ограничивать количество запросов, чтобы защитить downstream-сервис от перегрузки и не получить каскадный отказ.
  • Bulkhead — изолировать пул потоков/соединений для конкретной зависимости.
  • Correlation ID — прокидывать идентификатор операции через все сервисы.
  • OpenAPI-контракт — фиксировать методы, URL, схемы request/response и коды ошибок.
  • TLS и авторизация — сертификаты, токены, scopes, service account, mTLS.
Для сопровождения: rate limiter должен быть виден в метриках. Если появляются HTTP 429, нужно понимать, кто ограничивает трафик: сам сервис, API Gateway, Ingress, service mesh или внешний балансировщик.

6. Kafka

Как работает Kafka

Kafka — это распределённая платформа потоковой передачи событий. Producer пишет события в topic. Topic разделён на partitions. Consumer group читает события из partitions и хранит позицию чтения — offset.

Producer -> Kafka Topic -> Partitions -> Consumer Group -> Consumer instances
ПонятиеСмыслЧто важно поддержке
TopicЛогическая лента событий.Проверить имя topic, retention, количество partitions.
PartitionЧасть topic, даёт параллелизм и порядок внутри partition.Порядок гарантируется только внутри одной partition.
OffsetПозиция сообщения в partition.По offset видно, где находится consumer.
Consumer groupГруппа обработчиков, совместно читающая topic.Одна partition в рамках group читается только одним consumer.
LagОтставание consumer group от конца topic.Рост lag = consumer не успевает или не может обработать сообщения.

Kafka-кластер: brokers и ZooKeeper

Kafka работает как кластер из нескольких серверов — brokers. Каждый broker хранит часть partitions, принимает записи от producers и отдаёт данные consumers.

В классической архитектуре Kafka использует ZooKeeper для хранения метаданных кластера, координации broker-ов, выбора controller broker и управления состоянием. В более новых версиях Kafka может работать в режиме без ZooKeeper — через KRaft, где метаданные управляются самим Kafka-кластером. Но во многих enterprise-средах всё ещё встречаются кластеры с ZooKeeper.

Как достигается надёжность в Kafka

Надёжность Kafka достигается не одним параметром, а набором настроек на уровне topic, producer, broker и consumer.

МеханизмКак работаетПочему важно
Replication factorКаждая partition имеет несколько копий на разных brokers.При падении одного broker данные остаются на других.
Leader / follower replicasЗапись и чтение идут через leader partition, follower replicas копируют данные.Если leader падает, выбирается новый leader из актуальных replicas.
ISR — in-sync replicasНабор replicas, которые успевают синхронизироваться с leader.Если ISR уменьшается, надёжность снижается.
acks=allProducer считает запись успешной, когда подтвердили in-sync replicas.Повышает гарантию записи, но может увеличить latency.
min.insync.replicasМинимум replicas, которые должны подтвердить запись.Защищает от записи в единственную оставшуюся копию.
Idempotent producerЗащищает от дублей при retry producer-а.Важно при сетевых сбоях и повторных отправках.
TransactionsПозволяют атомарно записывать несколько сообщений и offset.Нужны для обработки без дублей и потерь в сложных сценариях.
RetentionKafka хранит события заданное время или объём.Позволяет повторно перечитывать события, но требует контроля места на диске.
Важно: Kafka не делает обработчик автоматически идемпотентным. Даже при надёжной записи в topic consumer может обработать сообщение повторно. Бизнес-операции должны учитывать дубли.

Когда выбирать Kafka

  • Нужен поток бизнес-событий между многими системами.
  • Нужно хранить историю событий и иметь возможность повторного чтения.
  • Высокая нагрузка и большой объём сообщений.
  • Одно событие должны независимо обработать несколько consumer groups.
  • Важна аналитика, аудит, захват изменений данных, событийная модель или потоковая обработка.

Частые проблемы: растёт consumer lag, consumer не коммитит offset, неверно выбран key и все события попали в одну partition, нарушен контракт сообщения, producer не может подключиться к bootstrap servers, ISR уменьшается, broker упёрся в диск или сеть.

7. RabbitMQ

Как работает RabbitMQ

RabbitMQ — брокер сообщений с очередями и гибкой маршрутизацией. Producer отправляет сообщение в exchange, exchange по правилам направляет его в queue, consumer читает из queue и подтверждает обработку через ack.

Producer -> Exchange -> Binding / Routing key -> Queue -> Consumer
ExchangeКак маршрутизируетПример
directПо точному routing key.crm.order.created
topicПо шаблону routing key.crm.order.*
fanoutВо все связанные очереди.Рассылка события всем подписчикам.
headersПо заголовкам сообщения.Маршрутизация по атрибутам.

RabbitMQ-кластер

RabbitMQ можно запускать как кластер из нескольких nodes. Кластер позволяет централизованно управлять пользователями, virtual hosts, exchanges, queues, bindings и политиками. Но важно понимать: сам факт кластера не означает, что каждая очередь автоматически полностью отказоустойчива.

Зеркалирование очередей, quorum queues и политики

В классических версиях RabbitMQ отказоустойчивость очередей часто делали через mirrored queues: очередь имела master и зеркала на других nodes. При падении master одно из зеркал становилось новым master.

В современных инсталляциях всё чаще используют quorum queues. Они основаны на репликации через консенсус и лучше подходят для надёжной доставки, чем старое зеркалирование classic queues.

ПодходЧто даётОграничения
Classic queue без зеркалированияПростая очередь на одном node.При проблеме node очередь может стать недоступной.

Как достигается надёжность в RabbitMQ

МеханизмКак работаетПочему важно

Messages unacked и prefetch count: чем опасны

Messages unacked — это сообщения, которые RabbitMQ уже отдал consumer-у, но consumer ещё не подтвердил их успешную обработку через ack.

Prefetch count ограничивает, сколько неподтверждённых сообщений broker может одновременно отдать одному consumer-у. Если prefetch слишком большой, один consumer может забрать много сообщений, долго их держать и не отдавать другим обработчикам.

СитуацияРискЧто делать
Unacked растётConsumer завис, медленно обрабатывает или не отправляет ack.Проверить логи consumer, thread pool, БД, внешние вызовы.
Prefetch слишком большойОдин consumer забрал много сообщений, остальные простаивают.Уменьшить prefetch, оценить время обработки и количество consumers.
Consumer упал с unackedСообщения вернутся в очередь и могут быть обработаны повторно.Проверить идемпотентность обработки.
Долгие unackedОчередь визуально может быть не большой, но работа фактически застряла.Мониторить не только ready, но и unacked.
Опасность: высокий prefetch + медленный consumer = сообщения «разобраны», но не обработаны. В очереди мало ready-сообщений, но бизнес-процесс стоит.

Чтение из одной очереди разными consumers

Если несколько consumers читают одну и ту же queue, RabbitMQ распределяет сообщения между ними. Одно конкретное сообщение получает один consumer. Это модель competing consumers.

Queue: order.processing
   |       |       |
   v       v       v
Consumer  Consumer Consumer
  A         B        C
ОсобенностьЧто значит
МасштабированиеДобавление consumers увеличивает параллельную обработку.
ПорядокГлобальный порядок обработки может нарушаться, потому что сообщения обрабатываются разными consumers с разной скоростью.
AckСообщение удаляется из очереди только после подтверждения.
Повторная доставкаЕсли consumer упал до ack, сообщение может быть доставлено другому consumer.
PrefetchОпределяет, сколько сообщений один consumer может держать без ack.
Когда это хорошо: очередь задач, где каждый заказ, файл или заявка должны быть обработаны одним свободным worker-ом. Когда осторожно: сценарии, где строгий порядок сообщений критичен.

Когда выбирать RabbitMQ

  • Нужна классическая очередь задач.
  • Важна гибкая маршрутизация сообщений через exchange и routing key.
  • Нужны ack/nack, TTL, retry, DLQ.
  • Нужно распределять задачи между worker-сервисами.
  • Не требуется хранить длинную историю событий как в Kafka.
Частые проблемы: messages ready растёт, messages unacked зависли, consumer отключился, сообщения ушли в DLQ, неверный routing key, очередь переполнена, prefetch настроен слишком большим, policy не применилась к нужной очереди, broker упёрся в memory watermark или disk alarm.

8. ArtemisMQ

Что такое ActiveMQ Artemis

Apache ActiveMQ Artemis — это высокопроизводительный неблокирующий брокер сообщений с открытым исходным кодом, написанный на Java. Это не просто «новая версия» классического ActiveMQ, а полностью переписанный с нуля проект, который пришёл ему на смену.

Artemis часто встречается в enterprise-средах, где важны стандарты, надёжная доставка, очереди, топики, транзакционность, поддержка JMS и интеграция со старыми и новыми системами.

Простая формулировка: ArtemisMQ — это универсальный enterprise-брокер, который может работать как классическая очередь задач, как pub/sub-брокер и как шлюз между системами с разными протоколами.

Зачем создавался Artemis

ЦельЧто это значитПочему важно для enterprise
Высокая производительностьНизкая задержка и высокая пропускная способность.Брокер должен выдерживать большие потоки сообщений без деградации.
Поддержка JMS 2.0Совместимость со стандартом Java Message Service.Многие корпоративные Java-системы интегрируются именно через JMS.
Гибкость развертыванияМожно запускать отдельно, встраивать в приложение или поднимать кластер.Подходит для разных архитектур: от монолита до Kubernetes.
Множество протоколовCore, AMQP, MQTT, STOMP, OpenWire и другие.Позволяет связать системы, написанные на разных стеках.

Что такое JMS

JMS — Java Message Service — это стандарт Java API для обмена сообщениями между приложениями. JMS описывает, как приложение отправляет, получает и подтверждает сообщения, но конкретную реализацию даёт брокер: например, ArtemisMQ.

JMS-понятиеЧто означаетАналогия

ConnectionСоединение приложения с брокером.Канал связи.
SessionКонтекст отправки/получения сообщений.Рабочая смена оператора.
QueuePoint-to-point очередь.Одну задачу забирает один исполнитель.
TopicPublish-subscribe канал.Одно объявление получают все подписчики.

Для поддержки: если система использует JMS, в настройках приложения ищите connection factory, destination, queue/topic name, acknowledgement mode, transaction mode и credentials.

Enterprise messaging

Enterprise messaging — это подход к обмену сообщениями в корпоративных системах, где важны надёжность, транзакционность, совместимость, безопасность, аудит и управляемость.

  • Сообщения не должны теряться при рестарте приложения или брокера.
  • Должны быть понятные гарантии доставки и подтверждения обработки.
  • Ошибочные сообщения должны уходить в DLQ, а не ломать весь поток.
  • Должны поддерживаться транзакции и интеграция с базами данных.
  • Нужны права доступа, TLS, разделение адресов и очередей.
  • Нужна возможность мониторинга и эксплуатации в production.

Ключевые концепции Artemis

Модели сообщений

Point-to-Point

Queues

Сообщение отправляется в очередь и потребляется ровно одним потребителем. Идеально для распределения задач: десять worker-ов обрабатывают заказы, и каждый заказ берёт один свободный worker.

Publish-Subscribe

Topics

Сообщение публикуется в topic и доставляется всем подписчикам. Например, событие «вышел новый пост» получают email-сервис, push-сервис и сервис кэширования.

Point-to-Point:
Producer -> Queue -> one Consumer

Publish-Subscribe:
Producer -> Topic -> Consumer A
                  -> Consumer B
                  -> Consumer C

Гарантии доставки

РежимКак работаетРиск/польза
Auto AcknowledgementБрокер считает сообщение доставленным после отправки consumer-у.Быстро, но при сбое consumer сообщение может считаться обработанным ошибочно.
Client AcknowledgementКлиент явно подтверждает успешную обработку.Стандартный подход для надёжной доставки.
TransactionalAck выполняется в рамках транзакции.Можно связать обработку сообщений и операции с БД в атомарный сценарий.
Durable SubscriptionsДля topics: сообщения сохраняются для отключившегося durable-подписчика.Полезно, если подписчик временно недоступен, но не должен пропустить события.
Persistent messagesСообщения сохраняются на диск.Защита от потери при рестарте брокера.
Важно: надёжность доставки не отменяет идемпотентность. При redelivery consumer может получить сообщение повторно.

Техническая архитектура Artemis

Высокая производительность Artemis достигается за счёт неблокирующего I/O, журналирующего хранилища и эффективной работы с объектами сообщений в JVM.

КомпонентКак работаетПочему быстро
Netty / non-blocking I/OОдин поток может обслуживать множество подключений.Не нужен отдельный поток на каждое соединение.
JournalПерсистентные сообщения пишутся в последовательный append-only журнал.Последовательная запись на диск быстрее случайной.
Message poolingВнутренние объекты сообщений переиспользуются.Снижается нагрузка на Garbage Collector.
Protocol handlersПринимают сообщения разных протоколов и переводят во внутренний формат.Брокер может быть шлюзом между разными системами.
[Клиенты: Producer / Consumer]
        |
        | Протоколы: Core, AMQP, MQTT, STOMP, OpenWire
        v
[Protocol Handlers]
        |
        | Внутренняя модель сообщений
        v
[Ядро Artemis: Non-blocking I/O, Routing, Journal]
        |
        | Persist / Read
        v
[Journal files on Disk]

Схема читается так: клиенты подключаются к Artemis по разным протоколам. На входе их встречают протокольные модули, которые переводят сообщения во внутренний формат. Далее ядро Artemis решает, куда маршрутизировать сообщение, нужно ли сохранить его на диск и как доставить consumer-у.

Кластеризация Artemis

Для отказоустойчивости и масштабирования Artemis можно объединять в кластеры. Есть два основных подхода: master-slave для высокой доступности и симметричный кластер для распределения нагрузки.

ПодходКак работаетДля чего нужен
Master-Slave Shared StoreMaster и Slave используют общее хранилище. При падении Master, Slave подхватывает файлы журнала.Высокая доступность без копирования журнала по сети, но нужен общий диск.
Master-Slave ReplicationSlave синхронно получает копию журнала Master по сети.Высокая доступность без общего диска.
Symmetric clusterНесколько брокеров равноправно связаны между собой. Сообщения могут перенаправляться между nodes.Масштабирование нагрузки и распределение consumers/producers.
Master-Slave:
Producer -> Master Broker -> Journal
                  |
                  v
              Slave Broker

Symmetric cluster:
Broker A <-> Broker B <-> Broker C
   |            |            |
Consumer A   Consumer B   Consumer C
Разница: master-slave в первую очередь про отказоустойчивость конкретного брокера, а симметричный кластер — про масштабирование и распределение сообщений между несколькими брокерами.

Когда выбирать ArtemisMQ

  • Нужна JMS-совместимость.
  • Есть enterprise-системы, которые уже используют JMS/AMQP.
  • Нужны очереди, топики, транзакционные сценарии.
  • Нужна надёжная доставка, redelivery, DLQ и durable subscriptions.
  • Нужно поддержать разные протоколы в одном брокере.
  • Нужна гибкая схема развертывания: standalone, embedded или cluster.

1. Зафиксировать симптом

Какая система, какой endpoint/topic/queue, время начала, сколько пользователей/операций затронуто.

Запущен ли consumer, есть ли ошибки обработки, коммитится ли offset/ack.

Схема сообщения, обязательные поля, версия API, формат даты, enum-значения.
