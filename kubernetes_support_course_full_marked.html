Главная идея Kubernetes: инженер описывает желаемое состояние, а кластер постоянно сравнивает его с реальностью и старается привести реальность к описанию.

1. Основы устройства кластера

Что такое Kubernetes-кластер

Kubernetes-кластер — это группа серверов, которые вместе запускают контейнерные приложения и следят, чтобы они работали в нужном количестве экземпляров.

Для поддержки удобно думать так: Kubernetes — это не просто «место, где крутится контейнер», а диспетчерская система. Она знает, какие приложения должны работать, где они запущены, сколько копий нужно и что делать при сбое.

Аналогия: кластер похож на торговый центр. Есть администрация, которая распределяет помещения и следит за правилами, и есть магазины, где реально работают сотрудники. Control Plane — администрация, Worker Nodes — этажи и помещения, Pods — отдельные торговые точки.

Две главные части кластера

Часть Роль Аналогия Что смотрит поддержка
Control Plane Управляет кластером и хранит желаемое состояние. Диспетчерская аэропорта. Доступен ли API, работают ли контроллеры, нет ли проблем планирования.
Worker Node Сервер, на котором реально запускаются Pods. Цех, где выполняется работа. Готова ли Node, хватает ли CPU/RAM, не упал ли kubelet.

Виды Node в кластере

В реальных Kubernetes-кластерах Node часто разделяют по назначению. Это помогает изолировать системные компоненты, бизнес-приложения, мониторинг и инфраструктурные сервисы друг от друга.

Вид Node Назначение Аналогия Что важно поддержке
Master / Control Plane Node Узел управляющего слоя. На нём работают компоненты управления: API Server, Scheduler, Controller Manager, etcd или часть этих компонентов. Диспетчерская и кабинет управления объектом. Проверять доступность API, состояние управляющих компонентов, etcd и отсутствие перегрузки. Обычно прикладные Pods на такие Node не размещают.
Worker Node Основной рабочий узел, где запускаются прикладные Pods: backend, frontend, batch-задачи, интеграционные сервисы. Производственный цех, где выполняется основная работа. Смотреть Ready/NotReady, нехватку CPU/RAM, DiskPressure, рестарты kubelet, ошибки image pull и события Pods.
Infra Node Узел для инфраструктурных компонентов, которые обслуживают приложения: Ingress Controller, DNS-дополнения, service mesh, registry-proxy, системные агенты. Инженерная зона здания: вентиляция, электрика, маршрутизация. Понимать, что сбой infra Node может повлиять сразу на много приложений: внешний вход, маршрутизацию, DNS или сетевые политики.
Monitoring Node Узел для систем наблюдаемости: Prometheus, Grafana, Alertmanager, Loki, агенты сбора логов и метрик. Пост охраны и диспетчерская с камерами. Если monitoring Node перегружена или недоступна, приложение может работать, но поддержка потеряет метрики, алерты или логи.
Важно: разделение Node обычно реализуют через labels, taints и tolerations. Поэтому при диагностике Pending Pods поддержке нужно проверять не только ресурсы, но и ограничения размещения.
kubectl get nodes --show-labels
kubectl describe node <node-name>
kubectl get pods -A -o wide

Базовая схема

Пользователь / CI/CD / kubectl
          |
          v
      API Server  <-- точка входа
          |
  +-------+---------+---------+
  |                 |         |
etcd          Scheduler  Controller Manager
  |                 |         |
  +-----------------+---------+
                    |
                    v
             Worker Nodes
                    |
                  kubelet
                    |
                   Pods

Простой пример

Вы описали: «приложение payment-api должно работать в 3 экземплярах». Это желаемое состояние. Если один экземпляр упал, Kubernetes замечает, что вместо 3 осталось 2, и запускает новый Pod.

Для поддержки: важно искать не только ошибку в контейнере, но и причину, почему кластер не смог восстановить желаемое состояние: нет ресурсов, Node NotReady, неправильный image, ошибка probes, неверные labels.

1.1 Как кластер принимает решения

Кто за что отвечает

Компонент Что делает Аналогия
API Server Принимает все запросы: kubectl, CI/CD, контроллеры. Единое окно заявок.
etcd Хранит состояние кластера. Журнал распоряжений и фактов.
Scheduler Выбирает Node для нового Pod. Диспетчер, который выбирает свободный зал.
Controller Manager Следит, чтобы реальность совпадала с желаемым состоянием. Менеджер смены, сверяющий план и факт.
kubelet Агент на Node: запускает и проверяет Pods. Бригадир на конкретной площадке.
Container Runtime Запускает контейнеры. Станок, который выполняет работу.

Что происходит при создании Deployment

1. Применить YAML
Инженер отправляет описание желаемого состояния через kubectl apply.
kubectl apply -f deployment.yaml
2. Передать запрос в API Server
API Server принимает запрос и проверяет его корректность.
3. Сохранить состояние в etcd
Описание Deployment становится частью состояния кластера.
4. Запустить работу контроллеров
Controller Manager видит, что нужны Pods, и создаёт ReplicaSet.
5. Выбрать Worker Nodes
Scheduler подбирает подходящие Node с учётом ресурсов и ограничений размещения.
6. Запустить контейнеры
kubelet на выбранных Nodes запускает Pods через container runtime.
7. Направить трафик
Service начинает направлять трафик на готовые Pods, которые прошли readinessProbe.

Аналогия с рестораном

Deployment — заявка: «на кухне должны работать 3 повара». Controller Manager проверяет, что поваров действительно 3. Scheduler решает, на какую кухню отправить нового повара. kubelet на конкретной кухне выводит повара на смену. Service — стойка выдачи заказов, которая не меняет адрес, даже если повара внутри сменились.

HPA, PDB и Anti-Affinity — что важно поддержке

Помимо базовых сущностей (Pod, ReplicaSet, Deployment), для стабильной работы приложения в production почти всегда используются дополнительные механизмы: HPA, PDB и anti-affinity.

Механизм Что делает Почему важно
HPA (Horizontal Pod Autoscaler) Автоматически масштабирует количество Pod по метрикам (CPU, память, кастомные метрики). Без HPA приложение может «захлебнуться» под нагрузкой или наоборот держать лишние ресурсы.
PDB (PodDisruptionBudget) Ограничивает, сколько Pod можно одновременно остановить (например, при обновлении Node). Без PDB можно случайно «уронить» все Pod при обслуживании кластера.
Anti-affinity Разносит Pod по разным Node. Если все Pod на одной Node — падение Node = падение сервиса.
Аналогия:
  • HPA — это автоматическое увеличение количества операторов при наплыве клиентов.
  • PDB — правило: «нельзя одновременно уволить всех операторов».
  • Anti-affinity — нельзя посадить всех операторов в одну комнату.
Для поддержки:
  • Если приложение падает под нагрузкой — проверьте, есть ли HPA.
  • Если во время работ кластер «роняет» сервис — проверьте PDB.
  • Если outage произошёл из-за падения Node — проверьте anti-affinity.

1.2 Что важно прикладной поддержке

Как думать при инциденте

В Kubernetes проблема редко ограничивается одной точкой. Нужно пройти цепочку: приложение → Pod → Deployment → Service → Node → конфигурация → сеть.

  1. Есть ли Pod? kubectl get pods
  2. Готов ли Pod? статус Ready, рестарты, события.
  3. Есть ли endpoints у Service? если endpoints пустые, трафик некуда отправлять.
  4. Совпадают ли labels и selectors? частая причина «Service есть, но не работает».
  5. Хватает ли ресурсов? Pending часто связан с CPU/RAM, quota или ограничениями Node.

Типовые симптомы

Симптом Возможная причина Первая проверка
Pod в CrashLoopBackOff Приложение стартует и падает. kubectl logs pod-name --previous
Pod в Pending Не хватает ресурсов или нет подходящей Node. kubectl describe pod pod-name
Service не отвечает Нет endpoints или неверный targetPort. kubectl get endpoints service-name
После деплоя 502/503 Pods не проходят readinessProbe. kubectl describe pod pod-name
Новая настройка не применялась ConfigMap изменён, но Pod не перезапущен. kubectl rollout restart deployment/name
Операционное правило: «ресурс создан» не значит «приложение работает». Проверяйте состояние, события, endpoints, readiness и фактический ответ сервиса.

2. Сущности Kubernetes

Зачем нужны сущности

Kubernetes управляется декларативно: вы описываете объекты, а кластер выполняет работу. Каждый объект отвечает за свою часть: запуск, масштабирование, сеть, конфигурацию, безопасность или хранение.

Запуск

Pod / Deployment

Контейнеры, реплики, обновления и откаты.

Доступ

Service / Ingress

Стабильный адрес внутри и снаружи кластера.

Настройки

ConfigMap / Secret

Параметры приложения без пересборки образа.

Карта основных сущностей

Namespace
  |
  +-- Deployment
  |      |
  |      +-- ReplicaSet
  |              |
  |              +-- Pod(s)
  |                    |
  |                    +-- Container(s)
  |
  +-- Service --selector--> Pod labels
  |
  +-- ConfigMap / Secret --> env, files, volumes
  |
  +-- Ingress --> Service --> Pod

2.1 Pod, ReplicaSet, Deployment

Pod

Pod — минимальная единица запуска в Kubernetes. Обычно в Pod находится один основной контейнер приложения. Иногда рядом есть sidecar-контейнер: например, агент логирования или прокси.

Аналогия: Pod — это квартира. Контейнеры внутри Pod живут по одному адресу, имеют общую сеть и могут общаться через localhost.
kubectl get pods
kubectl describe pod payment-api-7c9d
kubectl logs payment-api-7c9d

ReplicaSet

ReplicaSet следит, чтобы существовало нужное количество одинаковых Pods. Обычно вы не создаёте ReplicaSet руками: его создаёт Deployment.

Аналогия: норматив смены: «на линии должно быть 3 оператора». Если один ушёл, нужен новый.

Deployment

Deployment управляет жизненным циклом приложения: создаёт ReplicaSet, поддерживает количество реплик, выполняет rolling update и позволяет откатиться.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: payment-api
        image: registry.local/payment-api:1.2.0
        ports:
        - containerPort: 8080
Связь: Deployment выбирает свои Pods через selector. Labels в template должны совпадать с selector, иначе управление репликами нарушится.

2.2 Service, Ingress, DNS

Service

Service даёт стабильный адрес для группы Pods. Pods могут пересоздаваться и получать новые IP, но имя Service остаётся тем же.

Аналогия: Service — единый номер контакт-центра. Сотрудники меняются, но клиент звонит на один и тот же номер.
apiVersion: v1
kind: Service
metadata:
  name: payment-api-svc
spec:
  type: ClusterIP
  selector:
    app: payment-api
  ports:
  - port: 80
    targetPort: 8080

Критичная связь: selector Service должен совпадать с labels Pod. Если не совпадает, у Service будут пустые endpoints.

kubectl get service payment-api-svc
kubectl get endpoints payment-api-svc

Типы Service

Тип Когда используется Пример
ClusterIP Доступ только внутри кластера. backend-service для frontend.
NodePort Открывает порт на каждой Node. Тестовый доступ без балансировщика.
LoadBalancer Внешний балансировщик от облака или инфраструктуры. Входной публичный API.
ExternalName DNS-алиас на внешний адрес. Ссылка на внешний managed database endpoint.

Ingress

Ingress управляет HTTP/HTTPS-входом в кластер: маршруты по домену и пути, TLS, правила доступа. Сам Ingress обычно работает вместе с Ingress Controller.

internet
   |
   v
Ingress Controller
   |
   v
Ingress rule: payments.example.ru/api -> payment-api-svc:80
   |
   v
Service -> Pods

2.3 ConfigMap, Secret, Volume

ConfigMap

ConfigMap хранит неконфиденциальные настройки: адреса сервисов, режимы работы, feature flags, имена очередей.

Аналогия: ConfigMap — инструкция на стене: её можно заменить без пересборки приложения, но сотрудник должен заново прочитать инструкцию.
apiVersion: v1
kind: ConfigMap
metadata:
  name: payment-config
data:
  LOG_LEVEL: "info"
  CURRENCY_SERVICE_URL: "http://currency-svc"
Если ConfigMap подключён как переменные окружения, работающий Pod обычно не увидит новые значения без перезапуска.

Secret

Secret используется для чувствительных данных: паролей, токенов, ключей. Важно: base64 в Secret — это не полноценное шифрование для человека, а формат хранения значения.

kubectl get secret payment-secret
kubectl describe secret payment-secret

Volume и PersistentVolumeClaim

Volume подключает данные к Pod. Для временных данных можно использовать ephemeral volume, для постоянных — PersistentVolumeClaim.

Аналогия: Pod — временная машина. Volume — подключённый диск. Если машина сломалась, диск можно подключить к другой машине.
Сущность Задача Пример
Volume Дать контейнеру файловое пространство. Каталог для временных файлов.
PersistentVolume Реальное хранилище в кластере. Сетевой диск.
PersistentVolumeClaim Запрос приложения на хранилище. «Нужно 10Gi для данных».

2.4 Namespace, labels, probes

Namespace

Namespace разделяет ресурсы внутри одного кластера. Часто используются пространства по средам или командам: dev, test, prod-payments.

Аналогия: Namespace — отдельный кабинет в офисе. Люди работают в одном здании, но документы, права и ресурсы разделены.
kubectl get pods -n prod-payments
kubectl config set-context --current --namespace=prod-payments

Labels и selectors

Labels — метки объектов. Selectors — правила выбора объектов по меткам. На них держатся связи Deployment → Pod и Service → Pod.

metadata:
  labels:
    app: payment-api
    tier: backend
    env: prod
Для поддержки это одна из первых проверок: если метки не совпали, объект существует, но связь не работает.

Readiness и liveness probes

Probe Что проверяет Что происходит при проблеме
readinessProbe Готов ли Pod принимать трафик. Pod убирается из endpoints Service.
livenessProbe Жив ли процесс внутри контейнера. Контейнер перезапускается.
startupProbe Успело ли приложение стартовать. Защищает медленный старт от преждевременного рестарта. 
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

2.5 Связи сущностей Kubernetes

Главная цепочка приложения

Ingress
  |
  v
Service payment-api-svc
  selector: app=payment-api
  |
  v
Pods with label app=payment-api
  ^
  |
Deployment payment-api
  replicas: 3
  template labels: app=payment-api
  |
  +-- ConfigMap: payment-config
  +-- Secret: payment-secret
  +-- Volume/PVC: payment-data

Как читать YAML прикладной поддержки

  1. Найдите kind: это тип сущности.
  2. Найдите metadata.name и namespace: где объект живёт.
  3. Проверьте labels и selector: как объект связан с другими.
  4. Для Deployment проверьте replicas, image, env, resources, probes.
  5. Для Service проверьте port, targetPort, type, endpoints.

Пример диагностики: сервис не открывается

Симптом: payment-api недоступен
1. Проверить Pods
Смотрим Running, Ready и количество рестартов.
kubectl get pods -n prod-payments
2. Проверить события Pod
Ищем ошибки probes, image pull, ресурсов и планирования.
kubectl describe pod <pod> -n prod-payments
3. Проверить Service и endpoints
Понимаем, есть ли готовые Pods, на которые можно отправлять трафик.
kubectl get svc,endpoints -n prod-payments
4. Сверить labels и selector
Проверяем, выбирает ли Service нужные Pods.
kubectl get pods --show-labels -n prod-payments
5. Проверить логи приложения
Ищем прикладную ошибку, stack trace или проблему подключения.
kubectl logs deploy/payment-api -n prod-payments
Частая ошибка: после изменения имени приложения в labels забыли обновить selector Service. Deployment работает, Pods Ready, но Service не направляет трафик никуда.

3. Istio для прикладной поддержки

Что такое Istio

Istio — это service mesh, то есть слой управления сетевым взаимодействием между сервисами. Он помогает контролировать, как сервисы общаются друг с другом: куда идёт трафик, по каким правилам, с какой безопасностью и с какой наблюдаемостью.

Для прикладного администратора поддержки Istio важен потому, что часть проблем доступности может быть не в Pod, Deployment или Service, а в правилах маршрутизации, политике безопасности, mTLS, Gateway или VirtualService.

Простая аналогия: Kubernetes Service похож на внутренний номер отдела, а Istio — на умную телефонную станцию. Она может направить 90% звонков в старую версию сервиса, 10% в новую, запретить звонки без пропуска, записать статистику и показать, где именно произошёл сбой.

Зачем нужен Istio

Задача Что даёт Istio Пример для поддержки
Управление трафиком Маршрутизация по host, path, headers, версиям сервиса и весам. 10% пользователей отправили на новую версию payment-api, 90% оставили на старой.
Безопасность mTLS, политики доступа, проверка личности сервиса. Сервис catalog не может обратиться к payment-api без разрешения.
Наблюдаемость Метрики, трассировка, коды ответов, задержки, процент ошибок. Видно, что 503 появляется между frontend и backend, а не на внешнем балансировщике.
Отказоустойчивость Timeout, retry, circuit breaking. Если внешний сервис отвечает медленно, Istio ограничивает ожидание и повторяет запрос по правилу.
Безопасные релизы Canary, blue-green, traffic shifting. Новая версия проверяется на малом проценте трафика без полного переключения.

Как Istio работает технически

Обычно рядом с приложением в Pod запускается дополнительный контейнер-прокси — sidecar. Чаще всего это Envoy. Приложение продолжает работать как раньше, но сетевой трафик проходит через sidecar.

Клиентский сервис
      |
      v
Envoy sidecar  ---- правила Istio ---->  Envoy sidecar
      |                                      |
      v                                      v
Приложение A                           Приложение B

Благодаря этому Istio может управлять трафиком без изменения кода приложения.

Для поддержки: если приложение «живое», Pods Ready, Service имеет endpoints, но запросы всё равно падают, нужно проверить Istio-правила: Gateway, VirtualService, DestinationRule, политики авторизации и mTLS.

Типовые симптомы Istio-проблем

Симптом Возможная причина Что смотреть

503 UF / no healthy upstream Нет доступных endpoints, неверный subset или DestinationRule. Service, endpoints, labels, subsets.

3.1 Сущности Istio: Gateway, VirtualService, Service

Главная цепочка входящего трафика

В Kubernetes без Istio внешний трафик часто идёт через Ingress. В Istio для HTTP/HTTPS-входа обычно используются Gateway и VirtualService, а конечной точкой остаётся обычный Kubernetes Service.

Пользователь / внешний клиент
          |
          v
Istio Ingress Gateway
          |
          v
Gateway: принимает host и port
          |
          v
VirtualService: выбирает маршрут по host/path/header
          |
          v
Kubernetes Service
          |
          v
Pods приложения

Gateway

Gateway описывает, какой входящий трафик Istio должен принять: порт, протокол, host и настройки TLS. Gateway не решает, в какой Service отправлять запрос. Он только открывает «дверь» в mesh.

Аналогия: Gateway — это проходная здания. Она знает, какие двери открыты, по каким адресам можно прийти и нужен ли пропуск TLS.
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: payment-gateway
  namespace: prod-payments
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - payments.example.ru

Что проверяет поддержка: совпадает ли host, открыт ли нужный port, правильно ли выбран ingress gateway через selector, нет ли ошибки TLS-сертификата.

VirtualService

VirtualService описывает правила маршрутизации: какой host обрабатывать, какой path или header учитывать и в какой Kubernetes Service отправлять запрос.

Аналогия: VirtualService — это диспетчер на проходной. Он смотрит, куда именно идёт человек: в отдел платежей, кабинет возвратов или тестовую комнату новой версии.
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payment-vs
  namespace: prod-payments
spec:
  hosts:
  - payments.example.ru
  gateways:
  - payment-gateway
  http:
  - match:
    - uri:
        prefix: /api
    route:
    - destination:
        host: payment-api-svc
        port:
          number: 80

Что проверяет поддержка: совпадает ли host с Gateway, указан ли правильный gateway, верный ли path, правильное ли имя Service в destination.host, совпадает ли port.

Service в Istio-сценарии

Kubernetes Service остаётся обязательной точкой назначения. Istio не заменяет Service, а использует его как стабильный адрес группы Pods.

apiVersion: v1
kind: Service
metadata:
  name: payment-api-svc
  namespace: prod-payments
spec:
  selector:
    app: payment-api
  ports:
  - port: 80
    targetPort: 8080
Связь: VirtualService отправляет трафик в Service, Service выбирает Pods по selector, Pods должны иметь подходящие labels и проходить readinessProbe.

Как связаны Gateway, VirtualService и Service

Сущность Главный вопрос Типичная ошибка
Gateway Принимаем ли мы внешний трафик на нужный host/port? Host в запросе не указан в Gateway.
VirtualService Куда направить запрос после входа? Path не совпал, указан неверный gateway или Service.
Service Есть ли стабильная цель внутри Kubernetes? Пустые endpoints из-за несовпадения selector и labels.
Pod Есть ли живые экземпляры приложения? Pods не Ready, CrashLoopBackOff, ошибка readinessProbe.

Диагностика входящего запроса через Istio

Симптом: https://payments.example.ru/api не открывается
1. Проверить Gateway
Проверяем, принимает ли Istio внешний host и нужный порт.
kubectl get gateway -n prod-payments
kubectl describe gateway payment-gateway -n prod-payments
2. Проверить VirtualService
Проверяем host, gateway, path и destination Service.
kubectl get virtualservice -n prod-payments
kubectl describe virtualservice payment-vs -n prod-payments
3. Проверить Kubernetes Service и endpoints
Убеждаемся, что VirtualService ведёт в Service, у которого есть endpoints.
kubectl get svc,endpoints payment-api-svc -n prod-payments
4. Проверить Pods
Проверяем готовность Pods и события приложения.
kubectl get pods -n prod-payments -l app=payment-api
kubectl describe pod <pod> -n prod-payments
5. Проверить логи приложения и sidecar
Сравниваем прикладные ошибки и сообщения proxy.
kubectl logs <pod> -c payment-api -n prod-payments
kubectl logs <pod> -c istio-proxy -n prod-payments

Вопросы

Прогресс: 0/10 правильных ответов

1. Что хранит etcd?

Разбор: etcd хранит всё состояние кластера: какие есть объекты, сколько реплик, где они запущены. Это "источник правды" Kubernetes.

2. Что такое Pod?

Разбор: Pod — минимальная единица запуска. Именно внутри Pod запускаются контейнеры приложения, и все остальные сущности работают вокруг него.

3. Что даёт Service?

Разбор: Service даёт стабильный адрес. Даже если Pods пересоздаются и меняют IP, доступ к приложению остаётся через одно имя.

4. Почему endpoints Service могут быть пустыми?

Разбор: Самая частая причина — selector Service не совпадает с labels Pod или Pod не прошёл readinessProbe, поэтому не попал в endpoints.

5. Что делает readinessProbe?

Разбор: readinessProbe определяет, можно ли направлять трафик на Pod. Если probe не проходит — Pod исключается из Service, но не перезапускается.

6. Что делает sidecar (Envoy) в Istio?

Разбор: Envoy sidecar перехватывает весь сетевой трафик и применяет правила Istio (routing, retry, security).

7. Почему Service может работать, а запрос через Istio — нет?

Разбор: Istio добавляет слой маршрутизации — ошибка может быть именно в нём.

8. Что означает ошибка 503 (no healthy upstream) в Istio?

Разбор: 503 = нет healthy upstream (обычно endpoints пустые или ошибка routing).

9. Какая сущность принимает внешний трафик?

Разбор: Gateway — точка входа в Istio mesh.

10. Зачем нужен VirtualService?

Разбор: VirtualService управляет маршрутизацией: path, host, веса.

Что проверять при обращении

Вопрос Команда Что ищем
Приложение запущено? kubectl get pods Running, Ready, Restarts.
Почему Pod не готов? kubectl describe pod Events, probes, ресурсы, image pull.
Есть ли трафик к Pod? kubectl get endpoints IP готовых Pods.
Service выбирает нужные Pods? kubectl get pods --show-labels Совпадение labels и selector.
Что пишет приложение? kubectl logs Stack trace, ошибки конфигурации, подключения.
Итоговое правило: в Kubernetes нужно мыслить связями. Pod может быть жив, но Service не видит его. Deployment может быть создан, но Pods не стартуют. ConfigMap может быть изменён, но приложение не перечитало настройки.

Диагностика и самопроверка

Проверь свой кластер

  1. Открой Deployment и проверь: количество реплик, настроены ли HPA, PDB и probes (readiness/liveness).
  2. Проверь ресурсы: заданы ли в Deployment requests и limits по CPU/RAM.
  3. Проверь устойчивость: что произойдёт, если одна Node упадёт? Останется ли приложение доступным (реплики, распределение по Node, anti-affinity)?
Важно: эти проверки помогают найти проблемы до инцидента, а не после него.

Вопросы для самопроверки

  1. Объясните, что произойдёт с трафиком, если Deployment убьёт старый Pod и поднимет новый с новым IP — и почему клиент этого не заметит.

    Подумайте про роль Service и endpoints.

  2. Инженер говорит: «Обновил пароль от базы, нужно пересобрать образ». Что не так с этим утверждением и как выглядит правильный процесс?

    Вспомните про Secret и разделение кода и конфигурации.

  3. Pod в статусе Running, но сервис отдаёт 503. Какие 3 проверки вы сделаете в первую очередь?

    Подсказка: readiness, endpoints, labels.

  4. После деплоя новая версия приложения не принимает трафик. Какие причины возможны на уровне Kubernetes?

    Подумайте про readinessProbe, Service selector и rollout.

  5. Приложение доступно внутри кластера, но не открывается по домену снаружи. Где искать проблему?

    Подсказка: Ingress / Gateway / VirtualService.
